# 서재 1만 권 실험 (대용량 렌더링)

책 1만 권을 가진 서재를 만들어, 서재 화면이 어디서 느려지는지 재고 단계별로 고친 기록이다.
실제 회원 서재는 수백 권이지만, 다독가와 CSV 가져오기로 한꺼번에 들어오는 경우를 대비한 스트레스 테스트다.

## 결과 요약

책 10,000권 (공개 8,956권 · 책 소개 평균 190자), CPU 4배 느리게, 3회 중간값.

### 전체 보기 (`/lab_reader?year=all`, 책 8,498칸)

| 단계 | HTML(전송량) | TBT | DOM 노드 | 검색 입력 반응 | 스크롤 버벅임 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0. 수정 전 | 책장에 **1,000권만** 옴 (아래 "발견한 버그") | | | | |
| 1. 1,000권 잘림 수정 (기준선) | 17,982 KB | 8,808 ms | 56,230 | 696 ms | 13,686 ms |
| 2. + 보이는 단만 그리기 (가상화) | 13,776 KB | 4,584 ms | 7,164 | 96 ms | 2,766 ms |
| 3. + 화면이 쓰는 칸만 받기 | 7,989 KB | 3,534 ms | 7,163 | 104 ms | ~~1,467 ms~~ |
| 4. + 가상화 컴파일러 버그 수정 (실험 B 때) | **7,989 KB** | **3,839 ms** | **7,015** | **136 ms** | **3,367 ms** |

> 2·3단계의 스크롤 버벅임은 실제보다 작게 나왔다. React Compiler 가 가상화 결과를 재사용해서
> 스크롤해도 새 단을 그리지 않았기 때문이다(아래 "실험 B" 의 버그). 고친 뒤 4단계가 정상 동작의 숫자다.
> 그래도 기준선 13,686 ms 의 4분의 1이다.

### 연도 보기 (`/lab_reader`, 기본 화면, 올해 책 ~850칸)

| 단계 | HTML | TBT | DOM 노드 | 검색 입력 반응 |
| --- | ---: | ---: | ---: | ---: |
| 1. 기준선 | 13,403 KB | 3,937 ms | 7,186 | 96 ms |
| 2. + 가상화 | 12,977 KB | 3,390 ms | 2,149 | 56 ms |
| 3. + 칸 줄이기 | **7,191 KB** | **2,695 ms** | **2,148** | **56 ms** |
| 4. + 컴파일러 버그 수정 | 7,191 KB | 2,765 ms | 2,147 | 48 ms |

### 해 보고 쓰지 않은 것: CSS `content-visibility: auto`

책 소개 없는 데이터에서, 선반(`.shelf`)마다 `content-visibility: auto` 를 걸었다.

| | 검색 입력 반응 | 스크롤 버벅임 | TBT | DOM |
| --- | ---: | ---: | ---: | ---: |
| 기준선 | 848 ms | 11,191 ms | 3,144 ms | 56,056 |
| content-visibility | 216 ms | 1,517 ms | 3,420 ms | 56,054 |

한 줄로 큰 효과가 있었지만 쓰지 않았다.

- DOM 은 그대로라 첫 로딩(TBT)은 줄지 않는다. 기본 화면(연도 보기)은 선반이 하나라 효과가 없다.
- `content-visibility` 는 paint containment 를 걸어서, 선반 위로 삐져나오는 책 제목 말풍선이 잘린다.

## 발견한 버그: 1,000권이 넘으면 말없이 잘림

서재는 `books` 를 한 번에 받았는데, Supabase API 는 `max_rows`(기본 1000)를 넘는 행을 **에러 없이 잘라서** 준다.
1만 권을 넣었더니 책장에는 1,000권만 꽂혔다(`capped-10000.json`). 1,001권째부터 책장·통계·달력에서 빠진다.
지금은 1,000권씩 이어 받는다. 쪽을 나눠 받을 때는 순서가 늘 같아야 해서 `id` 를 정렬에 덧붙였다.

## 남은 병목

3단계 뒤에도 HTML 7~8MB, TBT 2.7~3.5초가 남는다. 원인은 **1만 권을 통째로 브라우저에 보내는 구조**다.
연도 요약·달력·배지·명함 같은 통계를 브라우저에서 전체 책으로 계산하기 때문에 지금은 다 보내야 한다.
다음 단계는 통계를 서버(DB 집계)로 옮기고 책은 연도별로 나눠 받는 것이다. 공사가 커서 따로 정한다.

## 다시 재는 법

```bash
supabase start                                   # 로컬 DB (Docker). 운영·dev 와 무관
node scripts/lab/seed-large-library.mjs 10000    # 로컬 주소가 아니면 아무것도 안 하고 멈춘다
# apps/page0127/.env.local 을 로컬 Supabase(127.0.0.1:54321)로 바꾼 뒤
cd apps/page0127 && npx next build --webpack && npx next start
node scripts/lab/measure-library.mjs my-run 3     # 결과: scripts/lab/results/my-run.json
```

측정 항목 설명은 `measure-library.mjs` 맨 위 주석에 있다.

## 한계

- 표지·책등 이미지를 비웠다(이미지 서버 속도가 섞이지 않게). 실제 서재는 이미지 책등이 많아 폭 어림이 덜 정확하다.
  그래서 단 나누기는 폭을 넓게 어림하고(24px) 쓸 수 있는 폭을 94%로 잡는다.
- 측정은 클라우드 Linux 컨테이너의 headless Chromium 이다. 절대값보다 단계 사이 비율을 본다.
- `results/` 의 `capped-*`, `fixed-10000`, `step1-cv-10000`, `step2-virtual-10000` 은 책 소개를 넣기 전 데이터라 위 표와 직접 비교하지 않는다.

# 실험 C: 캐시 켜고 끄고 부하 비교

같은 서버(로컬 운영 빌드)에 동시 접속 50으로 20초씩 요청을 몰았다. 세 페이지는 캐시 방식이 각각 다르다.

| 페이지 | 캐시 방식 | 캐시 켬 RPS | 캐시 끔 RPS | 캐시 켬 p50 | 캐시 끔 p50 | 캐시 끔 p99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `/books/info/[id]` | 페이지 통째로 (ISR, 1시간) | **836** | 96 | **56 ms** | 497 ms | 865 ms |
| `/books/all` | 데이터만 (`unstable_cache`) | 77 | 59 | 628 ms | 790 ms | 1,337 ms |
| `/lab_small` (150권 서재) | 없음 | 33 | (같음) | 1,402 ms | | |

에러는 모든 경우 0건. "캐시 끔"은 측정용으로만 로컬에서 바꿔 빌드했다(`revalidate` → `force-dynamic`, `unstable_cache` 를 거치지 않고 바로 조회). 리포 코드는 바꾸지 않았다.

## 읽는 법

- **페이지 캐시(ISR)는 서버 일을 거의 없앤다.** 처리량이 8.7배, 응답이 9배 빨라졌다. 렌더도 DB 도 건너뛰고 만들어 둔 HTML 을 준다.
  Vercel 에서는 이 응답이 CDN 에서 나가서 함수가 아예 안 돈다. 2026-11 CPU 한도 초과 때 ISR 로 바꾼 이유가 이것이다(#418).
- **데이터 캐시만으로는 CPU 가 별로 안 준다.** `/books/all` 은 1.3배 차이뿐이다. DB 조회는 건너뛰지만 React 렌더는 요청마다 한다.
  데이터 캐시는 DB 부하와 DB 지연을 막는 도구지, 함수 CPU 를 줄이는 도구가 아니다.
- **캐시가 없는 서재는 가장 느리다.** 서재는 로그인한 사람마다 다르게 보여서(주인/방문자) 페이지 캐시를 바로 쓰기 어렵다.

## 한계

- DB 가 같은 컴퓨터에 있어서 DB 왕복이 거의 0ms 다. 실제(Vercel 서울 ↔ Supabase 서울)는 왕복마다 수 ms 가 붙어서, 데이터 캐시의 효과는 이 표보다 크다.
- 부하 도구와 서버가 같은 4코어 컨테이너에서 돌았다. 절대 RPS 보다 켬/끔 비율을 본다.
- CDN 이 없다. 운영에서 ISR 페이지는 CDN 이 받으므로 서버 처리량 자체가 문제 되지 않는다.

## 다시 재는 법

```bash
node scripts/lab/seed-large-library.mjs 150 lab_small
LAB_BOOK_INFO_ID=<global_books id> node scripts/lab/load-test.mjs cache-on 50 20
```

# 실험 B: 피드 무한 스크롤 가상화

`lab_reader` 활동 1,000개(감상 0~6문장이라 카드 높이가 제각각)를 만들고, `/feed` 를 끝까지(50페이지) 내린 뒤 쟀다.
CPU 4배 느리게, 3회 중간값. 세 경우 모두 1,000개를 끝까지 불러왔다.

| 방법 | 그려진 카드 | DOM 노드 | JS 힙 | 스크롤 버벅임 | 버튼 반응 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기준선 (다 그림) | 1,000 | 27,642 | 32 MB | 3,822 ms | 176 ms |
| CSS `content-visibility: auto` | 1,000 | 28,641 | 32 MB | 902 ms | 80 ms |
| **TanStack Virtual (채택)** | **7** | **436** | **10 MB** | **184~350 ms** | **48 ms** |

## 왜 가상화를 골랐나

- `content-visibility` 는 그리기(paint)만 건너뛴다. DOM 과 메모리는 그대로라, 오래 켜 둔 휴대폰 탭에서 계속 쌓인다.
  피드의 메뉴·다이얼로그는 포털이라 서재 때처럼 잘리는 문제는 없었지만, 줄어드는 폭이 가상화보다 작다.
- 가상화는 화면 근처 카드만 남긴다. 카드 수가 1만 개가 돼도 DOM 은 거의 그대로다.

## 높이가 제각각인 목록

서재 선반(280px 고정)과 달리 카드 높이를 미리 모른다. 260px 로 어림해 자리를 잡고, 그린 카드는
`measureElement`(ResizeObserver)로 실제 높이를 재서 바로잡는다. 댓글을 펼쳐 카드가 커져도 아래가 밀린다.

다음 페이지 신호도 바꿨다. 목록 아래 감시 div(IntersectionObserver)는 가상 목록에서 "계속 보이는" 상태로 남아
신호가 다시 오지 않는 경우가 있었다. 지금은 "마지막으로 그린 카드 순번이 끝에서 3장 안"이면 부른다.

## 발견한 버그: React Compiler 와 가상화

`useWindowVirtualizer` 는 스크롤할 때마다 **같은 virtualizer 객체**를 돌려주고 안쪽 값만 바꾼다.
React Compiler 는 "입력이 같으면 결과도 같다"고 보고 `getVirtualItems()`·`getTotalSize()` 결과를 재사용한다.
그래서 피드는 60개에서 더 안 불러와졌고, 실험 A 의 서재(#455, 운영 배포됨)는 가운데로 내리면 선반이 빈 칸이었다.
두 가상화 컴포넌트에 `'use no memo'` 를 넣어 자동 메모에서 뺐다. 가상화 라이브러리를 쓰는 컴포넌트는 같은 처리가 필요하다.

## 알고 받아들인 손해

화면에서 멀어진 카드는 지워졌다 다시 그려진다. 그 카드의 댓글 펼침과 쓰다 만 댓글은 초기화된다.
좋아요·댓글 같은 서버 데이터는 react-query 캐시라 그대로다.

## 다시 재는 법

```bash
node scripts/lab/seed-large-library.mjs 10000    # lab_reader 와 책
node scripts/lab/seed-feed.mjs 1000              # lab_reader 활동 1,000개

```

피드 API 에는 로그인 사용자 60회/분 요청 제한이 있다. 측정 스크립트는 **로컬 DB** 의 `lab_reader` 카운터만 페이지마다 비운다.
앱의 요청 제한 코드는 바꾸지 않았다.
