# 컴포넌트 체크리스트

스토리를 "만들었다/안 만들었다"로만 세면 문서의 **질**이 보이지 않는다.
7개 항목 × 2점, **14점 만점**으로 채점해 무엇이 비었는지 드러낸다.

기준은 회사 디자인 시스템(`@bemily/design-system`)의 체크리스트를 이 프로젝트에 맞게
고친 것이다. 원본의 "코드 스니펫" 항목은 뺐다 — Storybook 이 각 스토리의 소스를 자동으로
보여주므로 따로 채점할 이유가 없다. 대신 **토큰 준수**를 넣었다. 이 프로젝트의 실제
관심사는 "값을 손으로 박지 않았는가"이기 때문이다.

---

## 그 전에 — 언제 디자인 시스템을 쓰나

채점보다 먼저 정할 것이 있다. **모든 UI 가 `shared/ui` 를 거치지는 않는다.**
그 경계가 코드에는 있는데 글로 적힌 적이 없어서, 네이티브 `<button>` 을 볼 때마다
"이건 실수인가?" 를 다시 판단해야 했다. 2026-07-30 에 전수 조사해 아래로 굳혔다.

### 시각적 형태를 갖는 컨트롤 → 디자인 시스템

배경·테두리·패딩을 가진 것, 즉 **"컨트롤처럼 생긴 것"** 은 예외 없이 `shared/ui` 를 쓴다.
높이·포커스 링·비활성 처리가 화면마다 갈리면 그걸 되맞추는 비용이 만드는 비용보다 크다.

실측(2026-07-30): 네이티브 `<input>` 직접 사용 **0곳**, `<textarea>` **0곳**.
`Button` 44 · `Card` 18 · `PageContainer` 17 · `BookCover` 14 · `Skeleton` 9 · `Input` 7.

### 형태 없는 클릭 영역 → 네이티브 `<button>`

**"눌리지만 버튼처럼 생기지 않은 것"** 에는 네이티브를 쓴다. 34곳이 그렇고 전부 같은 성격이다:

- 목록 항목 전체를 감싼 클릭 영역 (`NotificationItem` — `flex-1 space-y-1 text-left`)
- 입력칸 안의 X 지우기 아이콘 (`UserSearch` — `absolute right-3 top-1/2`)

여기에 `Button` 을 쓰면 **variant 를 전부 무력화해야 한다**(`variant='ghost'` + 패딩 제거 +
높이 해제 + hover 배경 제거…). 그건 컴포넌트를 쓰는 게 아니라 이기는 것이다.

### 도메인 셰이프 → CSS Module

Tailwind 로 표현이 번거로운 것만. 현재 2곳(`BookListItem` · `PublicBookShelf`)이고
책등 그라디언트·판형별 비율 유지가 그 이유다. 파일 상단에 07 문서 근거가 주석으로 있다.

새로 만들기 전에 **정말 Tailwind 로 안 되는지** 먼저 확인한다 — `.book-cover` 처럼
`globals.css` 유틸로 두는 방법이 먼저다.

### 판단이 애매할 때

**"이것과 똑같이 생긴 것이 다른 화면에도 나타날까?"** 를 묻는다.
그렇다면 DS 로, 이 화면에서만 쓰는 모양이면 그 자리에 둔다.
DS 로 올릴 때는 스토리와 이 체크리스트 채점이 함께 따라온다 — 그 비용을 치를 값이
있는지가 기준이다.

### 벗어난 것을 발견하면

2026-07-30 조사에서 하나 나왔다 — `BookRegistrationForm` 의 독서 상태가 네이티브
`<select>` 였다(같은 폼의 `Label`·`Switch` 는 DS 를 쓰는데). 근거 주석도 없어 의도인지
실수인지 알 수 없었고, `focus-visible` 링이 빠져 있었다.

**바꾸기 전에 "바꿔도 안전한가" 를 먼저 확인한다.** 그때 확인한 것:
폼이 `FormData` 를 쓰는지(네이티브 `name` 자동 수집에 의존하는지), `required` 가 실제로
검증에 쓰이는지, `htmlFor` 연결이 유지되는지. 셋 다 확인한 뒤 옮겼다.

## 채점 항목

### 1. 개요 (2점)

**무엇이고, 언제 쓰고, 언제 쓰지 않는가.** 컴포넌트 이름만 봐도 아는 내용을 다시
적는 건 0점이다. 판단이 필요한 지점을 적어야 한다.

- 2점: 용도 + 선택 기준(어느 variant 를 언제) + 쓰지 않을 자리
- 1점: 용도만
- 0점: 설명 없음

### 2. Props · 슬롯 문서 (2점)

`argTypes` 에 **카테고리**(Appearance / Content / State / Accessibility / Events)를
나누고 각 prop 에 설명과 기본값을 단다. 슬롯형(Card 등)은 조합 예시가 이를 대신한다.

- 2점: 카테고리 분류 + 설명 + 기본값
- 1점: 일부만
- 0점: 기본 추론에 맡김

### 3. 시각적 예시 (2점)

variant · size · state 를 **망라**한다. 눈으로 훑어 "이 컴포넌트가 할 수 있는 것"이
한 화면에 들어와야 한다.

- 2점: 6개 이상 스토리, 조합을 빠짐없이
- 1점: 3~5개
- 0점: 기본 하나

### 4. 접근성 (2점)

**addon-a11y 위반 0 은 최소 조건이지 만점 조건이 아니다.** 자동 검사가 못 잡는 것을
문서가 채워야 한다 — 키보드 조작, 스크린리더가 무엇을 읽는지, 언제 `aria-*` 가 필요한지.

위반 0 은 이제 **CI 가 강제한다** — `npm run test:storybook` 이 모든 스토리를 실제
Chromium 에서 렌더하고 axe 를 돌린다(2026-07-29 부터 `a11y.test: 'error'`).
그러니 이 항목의 1점과 2점을 가르는 건 오직 **설명이 있는가**다.

- 2점: 위반 0 + ARIA/키보드/스크린리더 설명
- 1점: 위반 0, 설명 없음
- 0점: 위반이 있거나 접근성 언급 없음

### 5. 하지 말 것 (2점)

가장 값이 나가는 항목이다. **잘못 쓰는 방법은 올바른 방법보다 가짓수가 많고**,
그 지식은 보통 누군가 한 번 틀린 뒤에야 생긴다. 적어 두지 않으면 다음 사람이 또 틀린다.

- 2점: 금지 사항 + 그 이유 + 대안
- 1점: 금지 사항만
- 0점: 없음

### 6. 실전 예시 (2점)

**진짜 화면의 한 조각**이어야 한다. 회색 상자에 "Content" 라고 적어 둔 건 실전이 아니다.
그 컴포넌트가 다른 컴포넌트와 함께 놓였을 때의 간격·위계가 보여야 한다.

- 2점: 실제 화면 조각 + 다른 컴포넌트와의 조합
- 1점: 단순 배치
- 0점: 없음

### 7. 토큰 준수 (2점)

색·크기·간격에 **하드코딩이 없어야** 한다. 그리고 07 문서의 원칙을 어기지 않아야 한다
(그림자 대신 1px 선, 유채색은 직무, 본문을 흐리게 칠하지 않기).

- 2점: 하드코딩 0 + 원칙 준수
- 1점: 사소한 예외가 근거와 함께 있음
- 0점: 하드코딩된 색·크기

## 현재 인벤토리 (2026-07-29)

사용량은 `import` 경로로 센 것이다. JSX 태그 이름으로 세면 다른 파일의 로컬 정의를
사용처로 잘못 집어 든다.

**채점은 후하게 하지 않았다.** 방금 쓴 문서라도 빈칸은 빈칸이다.

남은 감점과 이유:

- **`PageContainer` · `progress` 의 예시 1점** — 스토리가 5개·4개다. 상태 변화가 없는
  컴포넌트라 6개를 억지로 채우는 건 의미가 없어 **1점인 채로 둔다.** 항목을 못 채우는 게
  아니라 채울 필요가 없다는 판단이고, 그 판단을 여기 적어 두는 것이 점수보다 낫다.
- **`PageContainer` 의 하지말것 1점** — "너비는 화면 크기가 아니라 콘텐츠가 정한다"는
  기준은 있지만, 잘못 쓴 예를 보여주지는 않는다.
- **`BookCover` 의 하지말것 1점** — `.book-cover` 가 Tailwind 유틸을 이긴다는 경고는 있지만
  "그래서 무엇을 대신 하라"가 없다.

### 2026-07-29 2차 — Silver 3개를 메웠다

`card` 10 → **14**, `skeleton` 10 → **14**, `PageContainer` 9 → **12**.

채운 내용은 전부 **자동 검사가 못 잡는 것**이었다. 셋 다 addon-a11y 위반은 원래 0이었다:

- **`card`** — `Card` 도 `CardTitle` 도 `<div>` 라 스크린리더에는 제목이 아니다.
  구획이면 `<section aria-labelledby>` + `<h2>`, 목록이면 `<ul>/<li>` 로 **쓰는 쪽이
  의미를 준다**는 것을 스토리 두 개(`AsSection` · `AsListItems`)로 보였다.
- **`skeleton`** — 회색 블록은 장식이라 아무 말도 하지 않는다. 상태는 블록이 아니라
  **담은 영역**이 `role='status'` + `aria-live='polite'` 로 알린다.
- **`PageContainer`** — 이름 때문에 `<main>` 으로 만들고 싶어지지만 `<main>` 은 이미
  `AppShellLayout` 이 갖는다. 여기서 또 만들면 **랜드마크가 둘**이 된다.

### 2026-07-29 3차 — 사용처 4곳 이상을 전부 덮었다

`dialog` · `alert-dialog` · `textarea` · `avatar` · `ErrorBoundary` · `RelativeTime` 6개 추가.
**이제 사용처가 4곳 이상인 컴포넌트에는 모두 스토리가 있다.**

여기서도 자동 검사가 못 잡는 결함이 하나 나왔다 — `ErrorFallback` 에 `role` 도 `aria-*` 도
없어서, 화면이 에러 UI 로 갈아끼워져도 **스크린리더 사용자는 실패 사실 자체를 몰랐다.**
`role='alert'` 과 실제 `<h2>` 를 넣어 고쳤다.

### 스토리 없음

| 컴포넌트 | 사용처 |
| --- | ---: |
| `ReadCountBadge` · `label` | 각 3 |
| `ErrorFallback` · `SubmitButton` · `dropdown-menu` · `pagination` · `popover` | 각 2 |
| `scroll-area` · `select` · `sonner` · `switch` | 각 1 |

### 승격하며 드러난 것 — 텍스트 위계가 4단계에서 3단계로

`error` 로 올리자 위반이 **12개 요소**에서 나왔는데 원인이 하나였다:
`text-faint`(navy/300)가 흰 배경에서 **2.50:1**. 105곳에서 쓰였고 대부분이
알림 시각 · "/100" · "최근 7일" 같은 **읽어야 하는 정보**였다.

고치려니 4.5 를 넘기려면 `subtle`(5.05)과 육안 구분이 안 되는 값이 됐다 —
**4단계가 흰 배경에서 애초에 성립하지 않았다.** 그래서 `faint` 를 없애고 `subtle` 로
통합했다(105곳 치환). 캡션이 진해졌지만 이제 읽을 수 있다.

같이 고친 것: `ErrorFallback` 의 개발용 에러 박스가 `destructive/90`(투명도)로 흐려져
옅은 배경 위 4.04 였다 — 투명도를 걷어냈다.

**자동 검사는 바닥이지 천장이 아니다.** 2차 작업에서 채운 셋은 addon-a11y 위반이
원래 0이었는데도 접근성 0점이었다 — 검사가 잡는 건 "명백한 위반"뿐이고, `<div>` 로 만든
제목이나 아무 말 없는 로딩 상태는 잡히지 않는다. 그러니 `error` 로 올린 뒤에도
접근성 항목은 사람이 채워야 한다.
