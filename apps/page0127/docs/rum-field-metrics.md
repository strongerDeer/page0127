# 자체 RUM (실사용자 성능 측정)

> 작성 2026-07-27. 이 문서는 "왜 만들었나"와 "왜 이렇게 계산하나"를 남기는 판단 근거다. 구현 위치는
> 맨 아래 [파일 지도](#파일-지도) 참고.

## 1. 무엇이 문제였나

품질 파이프라인([quality.yml](../../../.github/workflows/quality.yml))은 주 1회 두 종류의 숫자를
쌓는다.

- **랩(Lighthouse)** — 앵커 5개 × 폼팩터 2개 × 3회 중앙값. `quality_records`에 저장.
- **필드(CrUX)** — 실사용자 28일 75분위. `quality_records.field` + `quality_field_history`에 저장.

이 중 **필드가 영원히 비어 있다.** CrUX는 표본이 임계를 넘는 origin/URL에만 데이터를 주고, 미달이면
404를 돌려준다([crux.ts:109](../../../packages/quality/src/crux.ts#L109)). page0127의 초기 목표
사용자는 10명 수준이라 오픈 후에도 임계를 넘지 못한다.

그래서 남는 건 랩 수치뿐인데, **랩 수치로는 합격/불합격을 판정할 수 없다.**

랩 LCP는 사실상 `전송량 ÷ 대역폭`이다. Lighthouse 모바일 프로파일은 느린 4G(1.6Mbps)·CPU 4배
스로틀·콜드 캐시로 조건을 고정하므로, 그 값은 "우리 사용자가 겪는 시간"이 아니라 "이 회선에서라면
걸릴 시간"이다. 실제로 형제 프로젝트에서 랩 LCP 11.7초 / 실사용자 LCP 1.44초가 동시에 나온 적이
있다. 랩은 **주차 간 상대 비교**(회귀 감지)에만 쓰고, 절대 판정은 필드로 해야 한다.

정리하면 오픈 시점의 상태는 이렇다.

|                 | 있음           | 판정에 쓸 수 있나 |
| --------------- | -------------- | ----------------- |
| 랩 (Lighthouse) | ✅             | ❌ 상대 비교 전용 |
| 필드 (CrUX)     | ❌ 트래픽 미달 | —                 |
| 필드 (자체 RUM) | ❌ 없었음      | —                 |

**판정 근거가 아무것도 없다.** 이 구멍을 메우는 게 자체 RUM이다.

## 2. 세 숫자는 각각 무엇을 재는가

셋을 한 값처럼 섞어 보면 안 된다. 재는 대상이 다르다.

|             | Lighthouse (랩)             | CrUX (필드)                    | 자체 RUM (필드)          |
| ----------- | --------------------------- | ------------------------------ | ------------------------ |
| 측정 대상   | 고정 조건의 1회 로드        | 익명 Chrome 사용자 집계        | 우리 방문자 개별 방문    |
| 조건        | 느린4G·CPU 4x·콜드캐시 고정 | 실제 회선·기기·캐시            | 실제 회선·기기·캐시      |
| 표본        | 3회 중앙값                  | 28일 이동창, 임계 이상         | 개별 샘플 전량           |
| 트래픽 임계 | 없음 (0명이어도 측정)       | **있음 (미달 시 데이터 없음)** | 없음                     |
| 브라우저    | Chrome                      | **Chrome 전용**                | 지표별로 다름 (§3)       |
| INP         | 측정 불가 (TBT로 대리)      | 있음                           | 있음                     |
| 지연        | 즉시                        | 최대 28일                      | 즉시                     |
| 쓰임        | 주차 간 상대 비교           | 절대 판정                      | 절대 판정 (표본 확보 시) |

**자체 RUM은 CrUX의 대체가 아니라 보완이다.** 트래픽이 늘어 CrUX가 채워지면 둘을 나란히 두고 대조할
수 있다 — 우리 계측이 맞는지 검증하는 기준선이 생기는 셈이다. 그래서 CrUX 수집 코드는 그대로 둔다.

### Vercel Speed Insights와의 관계

[layout.tsx](../app/layout.tsx)에 이미 `@vercel/speed-insights`가 붙어 있어 CWV를 보내고는 있다.
남겨 두되 이걸로 갈음하지 않는 이유:

- 데이터가 Vercel 대시보드 안에만 있다. 조회 API가 없어 **우리 DB로 못 가져온다** — 랩 수치 옆에
  나란히 놓거나, 회귀 판정에 쓰거나, 주간 리포트에 넣을 수 없다.
- 무료 플랜은 데이터 포인트 상한이 있고 넘으면 표본이 잘린다.
- attribution(무엇이 LCP 요소였나)을 볼 수 없다.

스크립트는 이미 로드돼 있고 비용도 없으니 **교차 검증용으로 남긴다.** 자체 RUM p75와 Speed Insights
p75가 크게 어긋나면 우리 계측을 의심할 신호가 된다.

## 3. 브라우저별로 무엇이 실제로 수집되는가

MDN 브라우저 호환성 데이터(2026-07 확인) 기준이다. **지표마다 지원 범위가 다르다** — 이걸 모르면
"Safari 사용자는 CLS가 좋다"는 식의 틀린 결론을 낸다. 실제로는 **오지 않은 것**이다.

| 지표 | 기반 API                               | Chrome | Firefox | Safari              |
| ---- | -------------------------------------- | ------ | ------- | ------------------- |
| TTFB | Navigation Timing                      | ✅     | ✅      | ✅                  |
| FCP  | Paint Timing                           | 60+    | 84+     | 14.1+ (iOS 14.5+)   |
| LCP  | `LargestContentfulPaint`               | 77+    | 122+    | **26.2+** (2025-12) |
| INP  | `PerformanceEventTiming.interactionId` | 96+    | 144+    | **26.2+** (2025-12) |
| CLS  | `LayoutShift`                          | 77+    | ❌      | ❌                  |

두 가지가 따라 나온다.

1. **CLS 표본은 Chromium 방문만 모인다.** p75를 계산할 때 "전체 방문의 75%"가 아니라 "CLS를 보고한
   방문의 75%"임을 명시해야 한다. 그래서 지표별 표본 수를 따로 저장하고 화면에도 따로 보여준다.
2. **LCP·INP는 최근 Safari에서 들어오기 시작했다.** CrUX는 Chrome만 보므로, iOS 비중이 큰 국내
   서비스에서는 자체 RUM이 CrUX보다 **더 넓게** 본다. 이게 자체 RUM의 부수 효과 중 가장 큰 것이다.

## 4. 왜 `quality_field_history`를 재사용하지 않았나

기존 테이블은 이렇게 생겼다
([마이그레이션](../../../supabase/migrations/20260724000001_create_quality_tables.sql)).

```sql
primary key (period_end, metric)   -- p75, good, needs_improvement, poor
```

여기에 자체 RUM을 넣으면 두 가지가 깨진다.

- **키 충돌.** 같은 `(period_end, metric)`에 CrUX p75와 RUM p75가 둘 다 들어오면 뒤에 쓴 쪽이 앞을
  덮어쓴다. 출처 컬럼을 추가해 키를 늘려도 다음 문제가 남는다.
- **창 길이가 다르다.** CrUX의 값은 **28일 이동창** p75이고, 우리가 주 단위로 접으면 **그 주**의
  p75다. 같은 컬럼에 담아 한 차트에 올리면 서로 다른 것을 잰 숫자를 한 선으로 잇게 된다.
- **저장 단위가 다르다.** CrUX는 이미 집계된 결과를 받아 적는 것이고, 우리는 개별 샘플을 받는다.

그래서 `quality_rum_samples`를 따로 만든다. 화면에서도 CrUX 패널과 자체 RUM 패널을 분리하고, 각 값에
출처를 붙여 표시한다.

## 5. 왜 원시 샘플로 저장하나 (집계는 읽을 때)

수집 시점에 히스토그램 버킷으로 접어 두는 방식도 있었지만 **원시 샘플 1행씩**을 택했다.

**근거 1 — 규모가 문제가 안 된다.** 사용자 10명 × 하루 5 페이지뷰 × 지표 5종 ≈ 250행/일, 연간 약 9만
행이다. Postgres에게 아무것도 아닌 크기다. 지금 접어 두는 건 조기 최적화다.

**근거 2 — 접으면 되돌릴 수 없다.** 히스토그램으로 저장하면 p75는 구간 근사치가 되고, 나중에 p95를
보거나 창 길이를 7일↔28일로 바꾸는 게 불가능하다. 원시로 두면 어떤 집계든 나중에 다시 계산할 수
있다.

**근거 3 — 이상치를 개별로 추적할 수 있다.** "LCP 12초짜리 방문이 1건 있었다"를 붙잡아 그 방문의
경로·기기·LCP 요소까지 볼 수 있다. 표본이 적은 초기에는 p75보다 이쪽이 훨씬 쓸모 있다.

**언제 롤업으로 바꾸나.** 행 수가 100만을 넘거나 대시보드 조회가 눈에 띄게 느려지면 일별 롤업
테이블을 추가하고, 원시 샘플은 보존 기간(180일)을 넘긴 것부터 자른다. 그 전까지는 안 만든다.

## 6. p75를 언제·어떻게 계산하나

### 언제 — 읽을 때

저장은 원시 그대로, 집계는 **대시보드가 조회할 때** 한다. 주간 워크플로에서 미리 계산해 두지 않는
이유는 §5와 같다(창 길이를 나중에 바꿀 수 있어야 한다). 조회 시 계산이라 주간 워크플로가 돌지 않은
날에도 대시보드는 항상 최신이다.

### 어떻게 — nearest-rank

지표별로 최근 N일 샘플을 오름차순 정렬한 뒤,

```
index = ceil(0.75 × n) - 1
```

번째 값을 취한다(nearest-rank). 보간하지 않는다 — 실제로 어떤 방문에서 관측된 값이라야 "이 사용자가
이만큼 기다렸다"로 읽을 수 있다.

**CrUX p75와 정확히 일치하지 않는다.** CrUX는 히스토그램 구간 기반 근사치를 쓰고 우리는 정확한
분위수를 쓴다. 둘을 대조할 때 수십 ms 차이는 정상이고, 배 단위로 벌어질 때만 계측을 의심한다.

### 표본이 적을 때 — 숫자를 지표인 척하지 않는다

샘플 5건의 p75는 숫자일 뿐 지표가 아니다. 표본 수에 따라 표시를 다르게 한다.

| 표본 수     | 표시                                                                    |
| ----------- | ----------------------------------------------------------------------- |
| n = 0       | "아직 수집된 샘플이 없습니다" — CrUX 데이터 없음과 **다른 문구**로 구분 |
| 0 < n < 10  | 값을 숫자로 보여주지 않는다. "표본 n건 — 아직 판정할 수 없음"           |
| 10 ≤ n < 30 | 값 표시. 단 판정 색은 중립(회색) + "표본 부족" 배지                     |
| n ≥ 30      | 값 표시 + CWV 표준 임계로 판정 색 적용                                  |

임계 30은 통계적 유의성이 아니라 **실무적 하한**이다. 이 규모에서 n=30이면 대략 며칠치이고, 그보다
적으면 방문 한 건이 p75를 통째로 흔든다.

> ⚠️ **"데이터 없음"과 "값 0"을 절대 섞지 않는다.** CrUX 파서에서 `Number(null) === 0` 때문에 결측이
> 완벽한 0으로 둔갑할 뻔한 전례가 있다([crux.ts:40](../../../packages/quality/src/crux.ts#L40)).
> 집계 함수는 `?? 0` / `|| []` 폴백을 쓰지 않고, 표본이 없으면 `undefined`를 반환한다.

## 7. 무엇을 하지 않는가 (비목표)

- **샘플링하지 않는다.** 100% 수집한다. 트래픽이 적은 게 문제인 상황에서 표본을 더 줄이는 건 자해다.
  샘플링은 일 1만 페이지뷰를 넘길 때 도입한다.
- **`user_id`를 붙이지 않는다.** 익명 세션 ID(난수, sessionStorage 수명)만 저장한다. 누가 느린
  기기를 쓰는지 알 수 있으면 유용하지만, 그건 개인별 성능 프로파일이고 개인정보처리방침에 없는
  수집이다.
- **IP를 저장하지 않는다.** 봇 판정에 쓰고 버린다.
- **경로를 원문 그대로 저장하지 않는다.** `/dreamfulbud/80a2…`는 사용자명과 책 ID를 품고 있고
  카디널리티가 높아 그룹핑이 안 된다. 서버에서 `/[username]/[bookId]` 같은 라우트 패턴으로 정규화해
  저장한다.
