# 홈 히어로 A/B — "당신의 인생책은?" 설계

> 2026-10-23 · 대화로 정한 방향을 구현 단위로 옮긴다. 배포는 10/26 기준선 측정 뒤
> (`00_docs/00_남은_작업_목록.md` 가입 유도 원칙 ②). 개발은 지금 한다.

## 1. 왜 하나

맛보기 히어로(10/8)는 "이 중에 읽은 책이 있나요?"로 **여러 권**을 고르게 한다. PR #228 은
"당신의 인생책은?" 컨셉에 맞춰 날짜 모르는 인생책을 기록할 수 있게 했지만, 그 질문을 던지는 화면은
아직 없다. 인생책 한 권은 읽은 책 열 권보다 고르기 쉽고(떠오르는 책이 하나는 있다), 서재 첫인상
(틸 테두리)이 되어 저장할 이유가 더 크다는 가설이다.

가설이라 **바꾸지 않고 나눠 본다.** 방문자가 적어 전후 비교로는 기간 효과와 섞이므로, 지금 화면(A)을
대조군으로 같은 기간에 함께 돌린다.

**성공 기준**

- 처음 온 비로그인 방문자가 50:50 으로 A/B 중 하나를 받고, 다시 와도 같은 쪽을 본다.
- B 에서 처음 고른 한 권은 로그인 뒤 서재에 **인생책**(평점 5 + `is_life_book`)으로, 완독일
  "모름"으로 담긴다. 지어낸 날짜가 들어가지 않는다.
- 어드민에서 `shelf_preview_pick → save → signup_start → sign_up → book_add` 를 A/B 로 나눠 본다.
- 스위치를 끄면 모두 A 를 본다(배포해 두고 10/26 뒤에 켠다).

## 2. 범위

**한다**: 그룹 배정(쿠키), 켜고 끄는 스위치, B 의 문구·고르기 흐름·책장 표시, 인생책 보관과 담기,
GA 사용자 속성, 어드민 깔때기 A/B 분리.

**하지 않는다**: 공개 서재 인생책 카드(히어로 실험이 끝난 뒤 — 원칙 ③), h1 변경("책장을 보면,
그 사람이 보인다."는 두 쪽 모두 같다 — 검색 노출 문장을 흔들지 않는다), 맛보기 단계의 별점 입력,
로그인 사용자 홈 변경, "나도 읽었어요"(책 상세) 흐름 변경.

## 3. 배정과 스위치

| 항목      | 정한 것                                                                        |
| --------- | ------------------------------------------------------------------------------ |
| 쿠키      | `hero_variant` = `a` \| `b`, 90일, `SameSite=Lax`, **httpOnly 아님**(5절 참고) |
| 배정 시점 | `proxy.ts` — 쿠키가 없고, 로그인하지 않았고, 경로가 `/` 일 때만                |
| 비율      | 50:50 (`Math.random() < 0.5`)                                                  |
| 스위치    | 서버 환경 변수 `HERO_AB=on`. 그 밖의 값이면 배정하지 않고 모두 A               |
| 렌더      | 홈 서버 컴포넌트가 쿠키를 읽어 `variant` 를 `ShelfPreview` 에 넘긴다           |

- **클라이언트 랜덤을 쓰지 않는 이유**: 서버가 그린 문구가 깜빡이며 바뀌고(하이드레이션 불일치),
  새로고침마다 그룹이 바뀌어 측정이 안 된다.
- **같은 요청에서 보이게**: 응답 쿠키만 심으면 그 요청의 서버 컴포넌트는 쿠키를 못 본다.
  `updateSession` 전에 `request.cookies.set` 으로 요청에도 넣는다.
- **스위치를 끄면** 이미 받은 쿠키가 남아 있어도 A 로 그린다(쿠키보다 스위치가 먼저).
- 경로를 `/` 로 좁힌 이유: 공개 서재·책 상세로 들어온 사람은 홈에 올 때 배정된다. 모든 경로에서
  배정하면 홈을 보지도 않은 사람이 그룹 수에 섞인다.

## 4. 화면

h1 과 레이아웃은 그대로다. 바뀌는 것은 소개 문장, 고르기 제목, 고른 책 표시뿐이다.

| 자리                   | A (지금)                                                  | B                                                                 |
| ---------------------- | --------------------------------------------------------- | ----------------------------------------------------------------- |
| 소개 문장              | 읽은 책을 골라 책장을 채워주세요. 당신의 취향은 어떤가요? | 가장 아끼는 한 권부터 꽂아 주세요. 언제 읽었는지 몰라도 괜찮아요. |
| 고르기 제목 (0권)      | 이 중에 읽은 책이 있나요?                                 | **당신의 인생책은?**                                              |
| 고르기 제목 (1권 이상) | (같음)                                                    | 또 읽은 책이 있나요?                                              |
| 고른 표지 표시         | 파란 링 + ✓                                               | 인생책: **틸 링 + 👑(Crown)** · 나머지: 파란 링 + ✓               |
| 내 책장                | 고른 순서                                                 | 인생책이 맨 앞, 틸 테두리(서재의 인생책 표시와 같은 색 `chart-6`) |

- 인생책 표지의 접근성 이름: `"{제목} (인생책)"`.
- 안내 문구(`toShelfPreviewMessage`)와 저장 버튼은 A 와 같다 — 한 번에 바꾸는 것을 줄인다.
- B 의 문구는 확정 전이다(12절 질문 1).

## 5. 고르기 규칙 (B)

상태에 `lifeBookIsbn: string | null` 을 더한다. 순수 함수 하나(`toggleLifeSelection`)로 둔다.

| 동작                  | 결과                                                                            |
| --------------------- | ------------------------------------------------------------------------------- |
| 인생책이 없을 때 고름 | 그 책이 인생책                                                                  |
| 인생책이 있을 때 고름 | 읽은 책으로 추가                                                                |
| 인생책을 뺌           | `lifeBookIsbn = null` → 제목이 다시 "당신의 인생책은?", 다음에 고른 책이 인생책 |
| 읽은 책을 뺌          | 인생책은 그대로                                                                 |
| 모두 비우기           | 둘 다 비움                                                                      |
| 검색으로 고름         | 목록에서 고른 것과 같은 규칙                                                    |

- 이미 고른 책을 인생책으로 **바꾸는** 동작은 1차에 넣지 않는다(빼고 다시 고르면 된다). 12절 질문 2.
- A 에서는 `lifeBookIsbn` 을 쓰지 않는다(항상 null).

## 6. 보관과 담기

**보관(localStorage `page0127:pending-shelf`)** — `v: 1` 을 유지하고 선택 필드를 더한다.

```ts
type PendingShelf = {
  v: 1;
  savedAt: number;
  books: PendingBook[];
  goal: PendingGoal | null;
  /** B 에서 고른 인생책. books 안에 있는 isbn 이어야 한다 */
  lifeBookIsbn?: string | null;
};
```

- 버전을 올리지 않는 이유: 배포 순간 남아 있는 보관분(24시간)이 전부 깨진다. 필드가 없으면 null 로 읽는다.
- 검증: 문자열이 아니거나 `books` 에 없는 isbn 이면 **null 로 버린다**(보관분 전체를 버리지 않는다).
- 다시 온 방문자: 책장과 함께 인생책 표시도 되살린다.

**담기(`PendingShelfClaimer` → `toBookInput`)** — 인생책 한 권만 다르게 담는다.

| 필드                                | 인생책        | 나머지 (지금과 같음) |
| ----------------------------------- | ------------- | -------------------- |
| `status`                            | `completed`   | `completed`          |
| `rating`                            | **5**         | 없음                 |
| `is_life_book`                      | **true**      | 없음                 |
| `completed_date` / `completed_year` | 비움 → "모름" | 비움 → "모름"        |

- 평점 5 + 플래그는 등록 폼과 같은 규칙이다(인생책은 최고점의 별칭 — `BookRegistrationForm`).
- 이미 서재에 같은 책이 있으면 지금처럼 건너뛴다(인생책 표시도 덮지 않는다).
- 로그인 화면 안내(`loginNotice`)는 바꾸지 않는다 — 권수만 말한다.

## 7. 측정 (GA4)

**그룹은 이벤트 파라미터가 아니라 사용자 속성으로 남긴다.**

- `gtag('set', 'user_properties', { hero_variant })` 를 **모든 페이지**에서 쿠키를 읽어 보낸다
  (`HeroVariantTracker`, 루트 레이아웃의 `GoogleAnalytics` 옆).
- 이유: 비교할 이벤트 대부분(`signup_start`·`sign_up`·`book_add`)이 홈이 아닌 로그인·온보딩·서재에서
  난다. 파라미터로 하면 그 이벤트마다 그룹을 실어야 한다. 쿠키가 httpOnly 가 아닌 이유도 이것이다.
- 스위치가 꺼져 있거나 쿠키가 없으면 보내지 않는다.

**이벤트 파라미터 추가 (B 에서만 의미가 있음)**

| 이벤트               | 추가 파라미터                   |
| -------------------- | ------------------------------- |
| `shelf_preview_pick` | `life: true` — 인생책이 됐을 때 |
| `shelf_preview_save` | `has_life_book: boolean`        |

**⚠️ 배포 전에 GA 에 등록한다 (원칙 ④)**

- 사용자 범위 맞춤 측정기준: 이름 `히어로 실험`, 사용자 속성 `hero_variant`
- 이벤트 범위 맞춤 측정기준은 1차에 등록하지 않는다(`life`·`has_life_book` 은 GA 탐색에서만 본다).

## 8. 어드민

유입분석의 이벤트 깔때기에 **A/B 나눠 보기**를 더한다. 기존 요청과 묶지 않고 따로 보낸다 —
`customUser:hero_variant` 가 등록되기 전에는 GA 가 400 을 주므로(`toCtaLocationRequest` 와 같은 이유).

```ts
dimensions: [{ name: "eventName" }, { name: "customUser:hero_variant" }];
```

- 표: 단계(행) × A·B(열), 각 칸에 사용자 수와 첫 단계 대비 비율.
- 앞 기간 비교는 넣지 않는다(실험은 같은 기간 안에서 비교한다).
- 한쪽이 30명 미만이면 "아직 판단하기 이르다" 문구를 함께 보인다.

## 10. 테스트

- vitest
  - `heroVariant`: 쿠키 값 검사(이상한 값 → 없음), 스위치 off → 항상 A, 배정 비율(난수 주입).
  - `toggleLifeSelection`: 5절 표의 여섯 줄.
  - `parsePendingShelf`: `lifeBookIsbn` 없음 → null, books 에 없는 isbn → null(보관분은 유지),
    문자열 아님 → null.
  - `toBookInput`: 인생책 → rating 5·is_life_book true·완독일 없음 / 나머지 → 지금과 같음.
  - GA 응답 파서: A/B 행 나누기, 한쪽만 있는 응답.
- 렌더: `ShelfPreview` 를 A/B 로 렌더해 제목·소개 문장·인생책 접근성 이름 확인.
- 수동(로컬): `HERO_AB=on` 으로 쿠키를 a/b 로 바꿔 가며 홈 확인, B 로 고르고 로그인 → 서재에서 인생책
  틸 테두리와 "모름" 확인.
- 회귀: 스위치 off 에서 홈 HTML 이 지금과 같다(쿠키가 b 여도 A).

## 11. 작업 단위 (커밋 하나 = diff 100~200줄)

7. 문서: 남은 작업 목록 갱신

## 12. 정해야 할 것

1. **B 문구** — 소개 문장 "가장 아끼는 한 권부터 꽂아 주세요. 언제 읽었는지 몰라도 괜찮아요." 와
   1권 뒤 제목 "또 읽은 책이 있나요?" 그대로 갈지.
2. **인생책 바꾸기** — 1차는 "빼고 다시 고르기"만. 고른 책을 눌러 인생책으로 바꾸는 동작이 필요한지.
3. **스위치 방식** — 환경 변수(켜려면 재배포 1번) vs 시작일 자동(`HERO_AB_START=2026-10-27`, 재배포
   없이 그날부터 켜짐). 기본안은 환경 변수(언제 켰는지 사람이 정한다).
4. **비율** — 50:50. 방문자가 적어서 한쪽으로 치우치게 둘 이유가 없다고 본다.
