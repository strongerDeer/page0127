### 1.1 라운드 2의 `dark:` 제거는 결과적으로 버그를 고쳤다

Tailwind v4 의 `dark:` 변형은 **기본값이 `prefers-color-scheme`** 이다(`.dark` 클래스가 아니다). 라운드 3 시점의 빌드 CSS 를 열어보니 제거 전 클래스들이 실제로 emit 돼 있었다:

```css
@media (prefers-color-scheme: dark) {
  .dark\:bg-input\/30 { background-color: var(--input); }
  .dark\:hover\:bg-input\/50:hover { … }
  .dark\:aria-invalid\:ring-destructive\/40[aria-invalid="true"] { … }
}
```

**토큰 값은 라이트 그대로였다.** 즉 OS 다크 사용자에게는 배경·글자는 밝은데 입력칸 몇 개만 어두운 **반쪽 상태**로 보였다. 라운드 2가 그 클래스들을 걷어내면서 화면이 최소한 일관돼졌다.

> 이 라운드는 그 자리를 **토큰 층에서** 제대로 채운다. `dark:` 유틸을 다시 뿌리는 게 아니라, 같은 변수의 값을 OS 설정에 따라 바꾼다.

## 3. 매핑 — 전부 측정값이다

배경은 `navy/900`(`#14294e`)이다. 아래 대비는 전부 그 위에서 잰 값이다.

### 3.1 글자

| 역할 | 라이트 | 다크 | 대비 |
|---|---|---|---|
| `text-strong` | navy/900 | **gray/0** | **14.41** — 라이트와 같은 값이다 |
| `text-body` | navy/700 | **gray/300** | 11.18 |
| `text-subtle` | navy/500 | **navy/300** | 5.76 |
| `text-faint` | navy/300 | **navy/500** | 3.21 (캡션) |

라이트의 `bg ↔ text-strong` 도 14.41 이다. **대비 수준을 그대로 옮겼다.**

### 3.2 면과 선

| 역할 | 라이트 | 다크 |
|---|---|---|
| `background` · `card` · `popover` · `sidebar` | gray/0 | **navy/900** |
| `sunken` · `secondary` · `muted` | gray/50 | **navy/800** (신설) |
| `line` | gray/300 | **navy/700** |
| `line-soft` | gray/200 | **navy/800** |

면 단차(`background ↔ sunken`)는 1.25 다. **면 단차는 대비 기준을 만족할 필요가 없다** — 보이기만 하면 된다. 07 §2.3 대로 입체는 그림자가 아니라 1px 선으로 만들고, 다크에서도 같다.

### 3.3 브랜드

| 역할 | 라이트 | 다크 | 대비 |
|---|---|---|---|
| `primary` | blue/600 | **blue/300** | 6.45 |
| `primary-foreground` | gray/0 | **navy/900** | 버튼 안 6.45 |
| `accent` | blue/50 | **navy/700** | — |
| `accent-foreground` | blue/700 | **gray/0** | 메뉴 안 8.37 |
| `ring` | blue/600 | **blue/300** | — |

**다크에서는 밝고 어두움이 뒤집힌다.** `blue/600` 은 navy/900 위에서 2.70 밖에 안 나와 링크색으로 못 쓴다. 밝은 파랑이 브랜드색이 되고, 그 위의 글자는 어두워진다.

`accent-foreground` 에 `blue/300` 을 쓰지 않은 이유: navy/700 위에서 3.74 라 14px 본문 기준(4.5)을 못 넘는다. 큰 글씨만 허용되는 값을 메뉴 항목에 쓸 수 없다.

## 4. 보강한 primitive 4개

색상(hue)·채도는 **원본 그대로** 두고 명도만 올렸다. "이 정도면 되겠지" 가 아니라, 목표 대비를 넘는 **가장 어두운 값**(= 원래 색에 가장 가까운 값)을 계산으로 찾았다.

| 이름 | 값 | 명도 | 근거 |
|---|---|---|---|
| `navy/800` | `#1b386b` | navy/900 과 navy/700 의 중간 | 다크 표면 단차. 라이트의 gray/50 자리 |
| `red/400` | `#dd7065` | 46% → 63% | destructive 가 다크에서 2.65 → 4.52 |
| `orange/400` | `#f0642d` | 45% → 56% | rank-up 이 3.35 → 4.51 |
| `slate/400` | `#627397` | 45% → 49% | chart-5 가 2.70 → 3.03 |

`violet/500` 은 3.17 로 이미 그래픽 기준을 넘어 **보강하지 않았다.**

## 5. 구현

### 5.1 토큰

- `tokens/dark.json` — `dark` 키 아래 **바뀌는 것만** 29개. 파생 토큰은 넣지 않는다.
- `build.mjs` — `css/variables-dark-media` 커스텀 포맷을 등록해 `dist/tokens-dark.css` 를 만든다.

기본 `css/variables` 를 못 쓰는 이유: 그건 selector 하나만 감싸는데 우리는 `@media (…) { :root { … } }` 로 **두 겹**을 감싸야 한다. 포맷이 이름에서 `dark-` 접두사를 떼는 이유는, 토큰 파일에서는 이름 충돌을 피하려 `dark` 아래 두지만 CSS 로 나올 때는 **같은 변수명이어야 라이트 값을 덮기** 때문이다.

라이트 파일 필터에 `token.path[0] !== 'dark'` 를 넣지 않으면 `--dark-background` 같은 **아무도 안 읽는 변수**가 `:root` 에 섞인다.

### 5.2 앱 연결

`globals.css` 가 라이트 **뒤에** 다크를 import 한다. 순서가 뒤집히면 덮어쓰기가 안 된다.

### 5.3 `.book-cover` 의 다크 처리

라운드 3에서 넘긴 항목이다. 흰 종이면(`#fff`)을 그대로 두면 표지 없는 책이 어두운 화면에서 튄다.

```css
@media (prefers-color-scheme: dark) {
  .book-cover {
    background-color: var(--sunken);
    /* 책등 음영은 검정이 안 먹으므로 흰 하이라이트로 뒤집는다 */
    background-image: linear-gradient(to right,
      rgba(255,255,255,0.1) 0px, rgba(255,255,255,0.04) 3px, transparent 8px);
  }
}
```

표지 이미지가 있으면 어차피 덮이므로 이 값은 **대체 조판에서만** 보인다.

## 6. 검증

### 6.1 토큰 구조 (`packages/design-tokens/tests/tokens.test.ts`)

다크용 테스트 5개를 추가했다. 가장 중요한 건 **이름 대조**다.

> 다크에만 있는 이름을 쓰면(오타 포함) 아무도 읽지 않는 변수가 조용히 생기고, 화면은 라이트 값을 그대로 쓴 채 **아무 에러도 나지 않는다.** 라이트에 같은 이름이 있어야만 덮어쓰기가 성립한다.

| 테스트 | 잡는 것 |
|---|---|
| `@media` 블록 안에 있다, `:root` 가 1개다 | 블록 밖으로 새면 라이트까지 덮는다 |
| **모든 다크 이름이 라이트에 존재한다** | 오타·유령 변수 |
| 다크 토큰이 `var()` 로 참조한다 | 리터럴이면 2층 구조가 깨진다 |
| 참조하는 원색이 라이트에 전부 있다 | 끊긴 참조 |
| 덮어쓸 토큰이 25개 이상이다 | 파일이 비어도 위 넷이 공짜로 통과하는 것 방지 |

**둘을 일부러 깨뜨려 확인했다** — 이름을 `--text-stong` 으로 오타 내니 이름 대조가 실패했고, `var(--blue-999)` 로 바꾸니 참조 테스트가 실패했다.

### 6.2 산출물 실측

**소스가 아니라 서빙되는 CSS 를 읽어** 변수 체인을 끝까지 해석하고 대비를 쟀다. `@import` 와 빌드를 거친 뒤의 값이 진실이기 때문이다.

| 대상 | 최종 색 | 대비 | 목표 |
|---|---|---|---|
| `--foreground` | `#fff` | **14.41** | 4.5 ✅ |
| `--card-foreground` | `#fff` | 14.41 | 4.5 ✅ |
| `--muted-foreground` | `#97a4c0` | 5.76 | 4.5 ✅ |
| `--text-body` | `#dfe3e8` | 11.18 | 4.5 ✅ |
| `--text-faint` | `#66779a` | 3.21 | 3.0 ✅ |
| `--primary` | `#74b0ff` | 6.45 | 4.5 ✅ |
| `--destructive` | `#dd7065` | 4.52 | 4.5 ✅ |
| `--rank-up` | `#f0642d` | 4.51 | 4.5 ✅ |
| `--line` | `#3b4e70` | 1.72 | 보이면 됨 ✅ |
| 주 버튼 안 | `#74b0ff` + `#14294e` | 6.45 | 4.5 ✅ |
| 호버 메뉴 안 | `#3b4e70` + `#fff` | 8.37 | 4.5 ✅ |

`--foreground` · `--card-foreground` · `--muted-foreground` 는 **다크에서 재정의하지 않았는데도** 올바른 값이 나온다 — 참조 구조가 의도대로 동작한다는 증거다.

## 7. 하지 않는 것

- **토글 UI** — OS 설정을 따르기로 했다. 나중에 필요하면 `next-themes` 가 이미 설치돼 있으므로 `.dark` 전략으로 바꾸면 된다(그때 이 `@media` 를 `.dark` 셀렉터로 바꾸는 것이 마이그레이션 전부다).
- **`sonner.tsx` 의 `useTheme`** — ThemeProvider 가 없어 항상 `system` 으로 떨어진다. sonner 자체가 `system` 을 OS 설정으로 해석하므로 결과적으로 맞게 동작한다. 건드리지 않는다.
- **`dark:` 유틸 재도입** — 이 라운드는 토큰 층에서 해결한다. 컴포넌트에 `dark:` 를 다시 뿌리면 라운드 2가 걷어낸 이유가 무의미해진다.
- **이미지·차트 라이브러리 색** — Recharts 등이 자체 기본색을 쓰는 곳은 별건이다.
- **다크 스크린샷 감수** — 실제 화면 확인은 사용자 몫으로 남긴다(§8).

## 7.5 Figma 완료 기록 (2026-07-29)

**Primitives 컬렉션** — 보강 4개 추가(`navy/800` `red/400` `orange/400` `slate/400`). 라운드 1 규칙대로 `scopes = []` 로 피커에서 숨기고 Code Syntax 를 심었다.

**Semantic 컬렉션** — `Dark` 모드 추가, 29개에 primitive alias 설정. 누락 0.

**Figma 와 코드가 일치한다.** 양쪽에서 같은 토큰을 해석해 대조했다:

| 토큰 | Light | Dark |
|---|---|---|
| `foreground` (파생) | `#14294e` | **`#ffffff`** |
| `card-foreground` (파생) | `#14294e` | **`#ffffff`** |
| `muted-foreground` (파생) | `#66779a` | **`#97a4c0`** |
| `border` (파생) | `#dfe3e8` | **`#3b4e70`** |
| `primary` | `#1e69cb` | `#74b0ff` |
| `primary-foreground` | `#ffffff` | `#14294e` |
| `destructive` | `#c0392b` | `#dd7065` |
| `background` | `#ffffff` | `#14294e` |
| `overlay` | `#000000` | `#000000` (양쪽 동일) |
| `chart/4` | `#d9a520` | `#d9a520` (양쪽 동일) |

**파생 토큰 4개가 재정의 없이 다크 값으로 해석된다** — 코드의 `var()` 체인과 Figma 의 alias 가 같은 방식으로 동작한다는 증거다.

**페이지 모드를 Dark 로 돌려 컴포넌트를 눈으로 확인했다.** 22개가 전부 따라왔다. 라운드 1부터 "하드코딩 색 0건" 을 고집한 값이 여기서 나온다 — 바인딩이 하나라도 빠졌으면 그 부분만 밝은 채로 남는다.

확인 중 **놓쳤던 검사를 하나 찾았다**: destructive 버튼 *안쪽* 대비(`red/400` 배경 + `primary-foreground` 글자)를 재지 않았었다. 재보니 **4.52 ✅** 였고, 만약 흰 글자였다면 3.19 로 미달이었다. 다크에서 `primary-foreground` 를 어두운 색으로 뒤집은 결정이 여기서도 값을 했다.

작업 후 페이지 모드는 **Light 로 되돌렸다** — 라이브러리의 기본 표시는 라이트다.
