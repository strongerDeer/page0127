# 트랙 E — 공유 카드 이미지 · 사용자별 동적 OG

작성일: 2026-07-28
브랜치: `worktree-track-e-share-og` (베이스: `origin/main` = `08f3be9`)

## 배경

6개 트랙 중 다섯 번째다. 트랙 B(60초 기록 의식)가 저장 직후 결과 카드를 만들면서
공유를 명시적으로 이 트랙에 미뤄 두었다:

> **공유 카드 이미지·사용자별 동적 OG** — 트랙 E. B2 의 결과 카드는 앱 안에서만 보인다.
> 그래서 결과를 라우트가 아닌 페이지 내 단계로 뒀다 — 공유 링크가 필요해지는 시점이
> 트랙 E이고, 그때 라우트로 올린다.
> (`2026-07-26-track-b-record-ritual-design.md` 195행)

## 착수 전 진단 — 문제는 이미지가 아니라 메타데이터다

공유 대상이 되는 공개 라우트의 현재 상태를 실제로 확인했다.

| 라우트                              | `generateMetadata`      | OG 이미지                        |
| ----------------------------------- | ----------------------- | -------------------------------- |
| `/` 홈                              | 있음 (`app/layout.tsx`) | 있음 (`app/opengraph-image.tsx`) |
| `/[username]` 공개 책장             | **없음**                | **없음** (루트 것으로 폴백)      |
| `/[username]/[bookId]` 공개 책 기록 | **없음**                | **없음** (루트 것으로 폴백)      |
| `/books/info/[id]` 책 정보          | 있음                    | 알라딘 표지 URL (세로 이미지)    |
| `/[username]/compatibility` 궁합    | 없음                    | —                                |

**즉 지금은 누구의 책장을 공유하든 카톡에 "page0127 - 책장을 보면, 그 사람이 보인다"
라는 같은 카드가 뜬다.** 링크를 받은 사람 입장에서 이 책장이 누구 것인지, 무엇이 들어
있는지 알 수 없다. 이미지를 예쁘게 만드는 것보다 **제목·설명이 그 페이지의 것이 되는 것**이
먼저다.

`/[username]/compatibility`는 **이 트랙의 범위에서 제외한다.** 로그인하지 않으면
`redirect('/login')` 으로 튕기는 페이지라(24–36행) 공유 링크가 성립하지 않는다.

`/books/info/[id]`의 OG는 **이번에 건드리지 않는다.** 알라딘 표지는 세로가 긴 이미지라
`summary_large_image` 슬롯(1.91:1)에서 좌우가 잘리지만, 그래도 "이 책"이 식별되기는 한다.
사용자 고유 콘텐츠가 없는 면이라 트랙 E의 목적(사람이 보이게)에서 벗어난다.

## 기술 제약 — 소스로 확인한 것

사용자가 지목한 **Vercel Hobby 1MB 한도**는 이미 해결된 문제이고, 되살리지 않는 것이
이 트랙의 제약이다. 관련 사실을 `node_modules` 소스에서 직접 확인했다.

### 1. 1MB는 Edge Function 한도였다 — 새 OG 라우트도 `runtime = 'edge'` 금지

`app/opengraph-image.tsx` 17–22행에 이미 기록돼 있다. `runtime = 'edge'` 일 때
next/og(satori + resvg wasm)가 통째로 실려 번들이 1.12MB가 됐고, Hobby 플랜의 1MB
한도를 넘겨 **빌드는 통과하는데 "Deploying outputs..." 에서 배포가 실패**했다.
런타임 지정을 지워 Node.js 서버리스로 돌리면서 해결됐다.

번들에 들어가는 자산 실측 (`node_modules/next/dist/compiled/@vercel/og/`):

| 파일                | 크기  |
| ------------------- | ----- |
| `index.node.js`     | 871KB |
| `resvg.wasm`        | 1.4MB |
| `yoga.wasm`         | 72KB  |
| `Geist-Regular.ttf` | 126KB |

합계 ~2.4MB. **Edge 한도의 두 배가 넘는다.** 새로 추가하는 OG 라우트에도
`export const runtime` 을 쓰지 않는다(= Next.js 기본값 Node.js 런타임).

### 2. 한글 폰트를 번들에 넣지 않는다 — next/og가 런타임에 subset을 받아온다

라이브 OG 이미지(`https://page0127.vercel.app/opengraph-image`)를 받아 확인한 결과
`fontFamily: 'sans-serif'` 만 지정했는데도 한글이 정상 렌더된다. 내장 폰트는
라틴 전용 Geist뿐인데도 그렇다.

이유는 `index.node.js` 의 `loadDynamicAsset` 이다. satori가 글리프를 못 찾으면
언어 코드를 넘겨 호출되고, 이 함수가 `languageFontMap` 에서 `'ko-KR' → 'Noto+Sans+KR'`
을 찾아 다음 URL로 **그 이미지에 등장한 글자만** 요청한다:

```
https://fonts.googleapis.com/css2?family=Noto+Sans+KR&text=<등장 글자>
```

**동적 텍스트(책 제목·닉네임·한줄평)도 폰트 번들 없이 렌더된다는 뜻이다.** 반대로
한글 폰트 파일을 직접 번들하면 2MB+가 함수에 얹혀 1MB 이슈를 되살린다. → **폰트를
번들하지 않는다.**

### 3. 폰트 fetch 실패는 예외를 던지지 않고 조용히 글자를 지운다

같은 파일의 `loadDynamicAsset` 은 실패를 이렇게 처리한다:

```js
} catch (e) {
  console.error("Failed to load dynamic font for", text, ". Error:", e);
}
```

`throw` 가 없다. 반환값이 `undefined` 가 되어 **그 글자만 사라진 채 200 OK 이미지가
나간다.** 배포는 성공하고 로그에만 남는다.

→ 설계 원칙 두 가지가 여기서 나온다.

- **텍스트를 짧게 자른다.** 글자 수가 적을수록 subset 요청이 가볍고 실패 확률이 낮다.
- **글자가 다 사라져도 형태가 남는 레이아웃으로 짠다.** 색면·책등처럼 텍스트가 아닌
  요소가 카드의 뼈대를 이루게 한다(지금 홈 OG의 책등이 이미 그 역할을 한다).

### 4. 죽은 표지 URL은 500이 아니라 **빈 자리**를 남긴다 (실측으로 정정)

착수 시점의 가정은 "표지 fetch가 실패하면 satori 렌더가 통째로 실패해 500이 나간다"
였다. 로컬에서 **실제로 404가 되는 알라딘 URL**로 확인한 결과 그렇지 않았다.

```
aladin cover: http=404
→ OG 라우트: http=200, image/png, 34KB (정상 렌더)
```

satori는 이미지를 못 받으면 **예외 없이 그림만 그리지 않는다.** 즉 200 OK 카드가
나가되 표지 자리만 텅 빈 채로 나간다. 폰트와 같은 실패 방식이다(제약 3).

→ 대응이 바뀐다. `try/catch` 로는 잡을 수 없으므로, **표지 자리에 색면을 먼저 깔고
그 위에 표지를 얹는다.** 표지가 안 그려지면 뒤의 색면이 그대로 보여 책 모양이 남는다.
(조회 실패용 `try/catch` 와 폴백 카드는 별개로 유지한다 — 그쪽은 예외를 던진다)

### 5. OG 이미지는 누가 보든 같아야 한다 — 쿠키를 읽지 않는다

기존 `createClient()`(`shared/config/supabase/server.ts`)는 `cookies()` 를 읽어
**보는 사람의 세션**으로 조회한다. OG 라우트에서 이걸 쓰면 소유자가 자기 OG URL을
직접 열었을 때 비공개 책까지 집계되어, 크롤러가 받은 이미지와 다른 숫자가 나온다.

→ OG 라우트 전용으로 **쿠키를 읽지 않는 익명 클라이언트**를 추가한다. 여기에
`is_public = true` 를 **직접 명시**한다(RLS는 익명 방문자만 걸러주므로 조건을 생략하면
세션 유무로 숫자가 갈린다 — `/books/info/[id]` 73–75행에서 같은 이유로 이미 명시하고 있다).

### 6. 기본 캐시 헤더는 매 요청 재생성이다

`next/dist/server/og/image-response.js` 가 붙이는 기본 헤더는
`public, max-age=0, must-revalidate` 다. 동적 OG를 그대로 두면 크롤러가 부를 때마다
Supabase 조회 + Google Fonts 왕복 2회가 일어난다.

→ 각 OG 라우트에서 `Cache-Control` 을 명시해 CDN에 붙인다. 책장·기록 내용은 자주
바뀌지 않고, 바뀌어도 공유 카드가 몇 시간 늦게 갱신되는 것은 허용된다.

## 설계

### E1. 공개 책장 `/[username]`

**메타데이터** — `generateMetadata` 를 새로 만든다.

- title: `{닉네임}님의 책장 | page0127`
- description: `{닉네임}님이 기록한 {N}권의 책. 책장을 보면, 그 사람이 보입니다.`
  (한줄 소개 `profile.bio` 가 있으면 그것을 앞세운다)
- 프로필이 없으면 404 페이지의 메타데이터를 돌려준다(페이지 본문이 이미 `notFound()`).

이름은 `toDisplayName()`(`entities/profile/model/displayName.ts`)을 그대로 쓴다 —
`nickname → username → '익명'` 순서가 화면과 어긋나면 안 된다.

**이미지** — `app/(public)/[username]/opengraph-image.tsx`

```
┌──────────────────────────────────────────────┐
│  page0127                                     │
│                              ▌▌█▌ ▌█▌▌        │
│  {닉네임}님의 책장            ▌▌█▌ ▌█▌▌        │
│                              ▌▌█▌ ▌█▌▌        │
│  12권 · 인생책 3권           ──────────       │
└──────────────────────────────────────────────┘
```

- 홈 OG의 잉크 배경(`#14294e`) + 책등 팔레트를 그대로 쓴다. 같은 서비스의 카드가
  두 종류로 보이면 안 된다.
- **책등 개수를 실제 공개 권수에 연동한다**(최대 8개, 0권이면 빈 선반). 카드가
  "이 사람의 책장"이라는 사실을 텍스트 없이도 전달하는 부분이다.
- 프로필 사진은 넣지 않는다 — 외부 이미지가 안 그려지면 빈 자리가 남는데(제약 4),
  이 면에서 그 리스크를 감수할 이유가 없다.
- 닉네임은 10자에서 자르고(넘치면 `…`), 그래도 첫 줄이 길면 글자 크기를 64→48px로
  줄인다. 줄이 접히면 "책장"이 셋째 줄로 밀려 카드가 어색해진다.
- 0권이면 점선으로 빈 자리를 그린다 — 선반 선만 남기면 렌더가 깨진 것처럼 보인다.

**조회** — 익명 클라이언트로 `profiles` 1건 + `books` count 2건(공개 전체 / 인생책).

### E2. 공개 책 기록 `/[username]/[bookId]`

**메타데이터** — `generateMetadata` 를 새로 만든다.

- title: `{책 제목} | {닉네임}님의 책장`
- description: 한줄평이 있으면 그것을, 없으면 `{닉네임}님이 읽은 {책 제목}({저자})`
- **비공개 책은 메타데이터를 만들지 않는다.** 페이지 본문은 소유자에게 비공개 책을
  보여주지만(54–56행), 메타데이터와 OG는 익명 기준으로만 만든다. 소유자가 자기
  비공개 기록 링크를 복사해 붙였을 때 한줄평이 미리보기로 새어 나가면 안 된다.

**이미지** — `app/(public)/[username]/[bookId]/opengraph-image.tsx`

```
┌──────────────────────────────────────────────┐
│  ┌────┐   {책 제목}                           │
│  │표지│   {저자}                              │
│  │    │   ★★★★☆                              │
│  └────┘   "{한줄평}"                          │
│           {닉네임}님의 책장 · page0127         │
└──────────────────────────────────────────────┘
```

- 표지 자리에 책등 색면을 깔고 그 위에 표지를 얹는다 — URL이 죽어 있으면 색면이
  그대로 보인다(제약 4). 표지가 없는 책도 같은 자리를 그대로 쓴다.
- 별점은 `toScore()`(`entities/book/model/rating.ts`)로 5점 척도 변환 후 채운 별/빈 별.
  **별은 '★' 문자가 아니라 SVG로 그린다** — 문자를 쓰면 심볼 폰트(Noto Sans Symbols)를
  한 번 더 요청하게 되고, 그 요청이 실패하면 별만 조용히 사라진다(제약 3).
  인생책(`rating === 10`)이면 별 5개 옆에 "인생책" 배지를 붙인다 — 화면에 이미 있는 표현이다.
- 별점을 매기지 않았으면 별 줄 자체를 그리지 않는다(빈 별 5개는 0점으로 읽힌다).
- 한줄평은 60자에서 자른다. 없으면 인용 블록 자체를 그리지 않는다(빈 줄이 남으면 안 된다).

### E3. 공유 버튼

지금 공유 수단은 `PublicLibraryHeader` 의 "서재 주소 복사" 하나뿐이다
(`navigator.clipboard.writeText`, 128–137행). 책 기록 페이지와 저장 직후 결과 카드에는
공유 수단이 아예 없다.

`src/features/share/ui/ShareButton.tsx` 를 만든다.

**`shared/ui` 가 아니라 `features/share` 인 이유**(착수 후 발견): `eslint.config.mjs` 의
`globalIgnores` 에 `src/shared/ui/**` 가 통째로 들어 있다. 주석은 "shadcn/ui 컴포넌트
제외(외부 라이브러리 코드)"인데, 실제로 그 폴더에는 직접 작성한 컴포넌트가 10개 넘게
섞여 있어(`ErrorBoundary`·`PageContainer`·`ProfileLink`·`SubmitButton` 등) **자체 코드가
린트를 못 받고 있다.** 공유는 사용자 시나리오이므로 FSD상 feature 가 맞기도 하다.
(기존 파일들을 `globalIgnores` 밖으로 꺼내는 것은 이 트랙의 범위가 아니다 — 별건)

- `navigator.share` 가 있으면 네이티브 공유 시트(모바일에서 카톡·메시지로 바로 간다),
  없으면 클립보드 복사 + 토스트로 떨어진다.
- 사용자가 공유를 취소하면(`AbortError`) 아무 말도 하지 않는다 — 취소는 실패가 아니다.
- 붙이는 곳 2군데:
  1. `PublicLibraryHeader` — 기존 "주소 복사" 버튼을 이걸로 교체
  2. `/[username]/[bookId]` 페이지 헤더 — `is_public` 인 기록에만 (비공개 링크는
     남이 열면 404 라 공유해도 소용없다)

**`BookSavedCard`(저장 직후)는 이번 범위에서 뺀다.** 공유 URL이 `/{username}/{bookId}`
인데 등록 페이지에서 `username` 을 알 수 없다 — `useCurrentUser` 가 쓰는
`/api/auth/me` 는 `{ id, email }` 만 돌려준다. username 을 얻으려면 그 API 응답을
넓혀야 하고, 그 API는 `CurrentUserProvider` 가 **모든 페이지에서** 호출하므로
전 페이지에 profiles 조회가 한 번씩 붙는다. 공유 버튼 하나를 위해 치를 비용이 아니다.
저장 직후 화면에는 이미 "내 책장 보기" 가 있고, 그 책장에 공유 버튼이 있다.

## 검증

각 단계 공통:

```bash
cd apps/page0127 && npm run lint && npm run type-check && npm test && npm run build
```

OG 이미지는 빌드만으로는 확인되지 않는다. 로컬 dev에서 실제 PNG를 받아 눈으로 본다:

```bash
curl -sS -o /tmp/og-library.png http://localhost:3000/<username>/opengraph-image
```

**한글이 깨졌는지는 반드시 이미지를 열어서 확인한다** — 제약 3 때문에 글자가 사라져도
HTTP 200에 정상 크기 PNG가 나온다. 상태 코드로는 판별되지 않는다.

배포 후에는 `curl -I` 로 `Cache-Control` 이 의도대로 붙었는지 확인한다.

## 개정 (2026-07-29) — 스카이 톤 정렬 + 닉네임 잘림 수정

배포 후 실사용 계정으로 확인하면서 두 가지가 드러났다.

### 1. 카드가 앱과 정반대 톤이었다

카드 배경으로 쓰던 `#14294e` 는 앱에서 **본문 글자색**(navy.900 = `foreground`)이다.
정작 공개 서재 화면은 흰 배경에 `#e3eefc` 스카이 틴트 면(blue.50 = `accent`)이라,
링크를 눌러 들어가면 카드와 화면이 다른 서비스처럼 보였다.

→ 팔레트를 앱의 시맨틱 토큰에서 그대로 파생한다. 카드는 **공개 서재 헤더와 같은 면**이다.

| 역할        | 값        | 앱 토큰                        |
| ----------- | --------- | ------------------------------ |
| 카드 배경   | `#e3eefc` | `accent` (blue.50)             |
| 브랜드·숫자 | `#0455bf` | `accent-foreground` (blue.700) |
| 본문        | `#14294e` | `foreground` (navy.900)        |
| 보조        | `#66779a` | `muted-foreground` (navy.500)  |
| 인생책      | `#d9a520` | `chart-4` (amber.500)          |

### 2. 책등이 막대그래프로 읽혔다

오른쪽 구석에 책등 8권을 세로로 모아 둔 구성이었다. 원래 주석도 "벌리면 막대그래프로
보인다"고 걱정하고 있었는데, 밝은 배경으로 바꾸니 그 인상이 더 뚜렷해졌다.
게다가 상한이 8권이라 **155권을 읽은 사람도 8권으로 보였다.**

→ 선반을 **카드 폭을 가로지르는 형태**로 편다. 실제 책장은 벽면을 가로지르고,
1200×630 가로 카드에도 그 비율이 맞는다. 세 카드(홈·책장·책 기록)가 이 선반을
공통 형태로 쓴다 — 책 기록 카드에서는 그 책 한 권이 같은 선반 위에 선다.

상한은 "몇 권"이 아니라 **선반 폭**으로 잡는다(`SHELF_WIDTH` 1072px). 개수로 자르면
오른쪽에 빈 자리가 남아 카드 좌우가 어긋난다. 남는 자리가 책 한 권 폭 이상이면
마지막 한 권을 그 폭으로 채워 선반이 양끝까지 이어지게 했다(실측: 좌 64 / 우 65).

### 3. 영문 닉네임이 불필요하게 잘렸다

`stronger_deer`(13자)가 `stronger_d…` 로 잘렸다. `truncate` 가 **글자 수만** 세고
문자 폭을 보지 않았기 때문이다. 라틴 글자는 한글의 절반 남짓 폭이라
`stronger_deer` 는 한글 8자 정도이고, 자를 이유가 없었다.

→ `textWidth()` 로 폭을 근사해(한글·CJK·이모지 1.0, 그 외 0.55) 그 기준으로 자른다.
제목 글자 크기도 폭으로 고른다.

### satori 관련 실측 메모

- **`gap` 을 쓰지 않는다.** 두 `Stat` 사이 `gap: 30` 이 먹지 않아
  "155권인생책 17권" 처럼 붙어 렌더됐다. 간격은 전부 `margin` 으로 준다.
- **`Fragment` 로 flex 자식을 묶지 않는다.** 위 증상의 원인이었다 — 두 항목을
  `<>...</>` 로 묶으면 flex 자식으로 세지 못한다. 조건을 각각 건다.
- 책등은 `position: absolute` + `left` 로 깐다. flex 로도 **같은 픽셀**이 나오지만
  (둘을 렌더해 바이트까지 대조했다), 좌표가 코드에 적혀 있어야 선반이 카드 폭을
  넘는지 계산으로 확인할 수 있다.
- 카드 검증은 눈대중이 아니라 **픽셀로** 한다. 브라우저에서 canvas 에 그려 한 행의
  색 전환을 세면 책등 개수·폭·간격이 정확히 나온다. 눈으로는 1px 간격을 15px 로
  잘못 읽었다.
