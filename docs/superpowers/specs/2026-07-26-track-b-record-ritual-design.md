# 트랙 B — 60초 완독 기록 + 첫 권부터 즉시 보상

작성일: 2026-07-26
브랜치: `worktree-track-b-record-ritual` (베이스: `main` = `cca03be`, 트랙 A 포함)

## 배경

외부 제품 리뷰를 6개 트랙으로 쪼갠 것 중 두 번째다. 트랙 A(오픈 전 데이터 정합성)는
`cca03be` 로 main 에 병합됐다 — 방문자가 보는 **숫자가 틀리지 않게** 만든 작업이었다.
트랙 B는 **사람이 다시 오게** 만드는 쪽이다.

리뷰가 지적한 두 문제:

1. **첫 보상이 너무 늦다.** 취향 분석은 별점 있는 완독 5권이 필요하다. 월 1~2권 읽는
   타깃 사용자는 첫 보상까지 몇 달이 걸린다.
2. **완독 기록이 "1분 의식"으로 설계되지 않았다.** 저장 후 서재로만 이동하고, 결과도
   공유할 것도 주어지지 않는다.

이 트랙이 증명해야 하는 제품 약속은 리뷰가 뽑아낸 이 문장이다:

> 책을 덮은 뒤 1분. 떠오른 생각을 잃기 전에 남기는 나만의 책장.

## 목표

책을 덮은 직후 **화면에서 결정할 것이 3개**이고, 저장하면 **내가 쓴 문장이 되돌아오는**
흐름을 만든다.

## 착수 전 발견 — 폼의 기본값은 이미 옳다

리뷰는 등록 폼이 "상태, 완독일, 시작일, 점수, 한줄평, 메모, 태그, 공개 여부"를 요구한다고
읽혔지만, `BookRegistrationForm.tsx` 의 초기 상태를 실제로 확인한 결과 기본값이 이미 옳다:

| 필드 | 기본값 |
| --- | --- |
| `status` | `'completed'` |
| `completedDate` | 오늘 |
| `isPublic` | `true` |

즉 **완독 등록에 실제로 필요한 입력은 0개**다. 리뷰의 정확한 표현도 이것이었다 —
"대부분 선택 사항이지만 사용자는 시각적으로 긴 폼을 만납니다."

**따라서 B1은 폼 재설계가 아니라 순서 바꾸기와 접기다.** 리듀서·제출 로직·저장되는
데이터는 그대로 둔다. 이 발견으로 트랙 B의 비용이 크게 줄었다.

## 설계

### B1. 기록 흐름 — 승격과 접기

`apps/page0127/src/features/book/ui/BookRegistrationForm.tsx` 한 파일.

현재 순서: 미리보기 → 독서 상태\* → 완독일\* → 시작일 → 평가 점수 → 한줄평 → 메모 →
태그 → 공개 여부 → 버튼

바꿀 순서:

```
미리보기                        (그대로)
독서 상태                        (그대로 — 완독이 기본, required 유지)
── 이하 status === 'completed' 일 때만 ──
"이 책을 한 문장으로 남긴다면?"   (한줄평: 6번째 → 3번째로 승격, autofocus)
평가   0점 … 5점 · 인생책
▸ 더 남기기                      (접힘)
      완독일 · 시작일 · 나만의 메모 · 태그 · 공개 여부
[저장]
```

**접기 구현은 네이티브 `<details>`/`<summary>`** 를 쓴다. 저장소가 이미 그 방식을 쓴다
(`src/features/admin-errors/ui/ErrorList.tsx`). shadcn collapsible/accordion 은 설치되어
있지 않으므로 새로 끌어들이지 않는다. 그 파일의 주석에 적힌 함정도 그대로 적용된다:
`summary` 에 직접 `flex` 를 주면 펼침 삼각형 마커가 사라지므로 안쪽 `span` 으로 정렬한다.

**펼침 기본값:** `open={!!initialData}`. 신규 등록은 접힌 상태, 수정 화면은 펼친 상태로
시작한다. 수정하러 온 사용자는 의도적으로 필드를 찾고 있기 때문이다. 신규·수정이 같은
컴포넌트를 공유하므로(`app/(protected)/books/add/page.tsx` 와
`src/widgets/book/ui/BookEditPageClient.tsx`) 이 한 줄로 갈린다 — 컴포넌트를 쪼개지 않는다.

**한줄평 문구:** 현재 `Label` 은 "한줄평", `placeholder` 는 "이 책에 대한 한줄평을
남겨주세요" 라는 작업 지시문이다. 둘 다 바꾼다:

- `Label`: `이 책을 한 문장으로 남긴다면?`
- `placeholder`: `덮고 나서 남은 생각을 그대로 적어도 좋아요`

지시문("남겨주세요")이 아니라 질문과 허락으로 바꾸는 것이 요점이다 — 잘 쓸 필요가 없다는
신호를 줘야 손이 움직인다. `autoFocus` 를 준다.

#### 완독일의 `required` 를 반드시 제거한다

접기 안으로 들어가는 필드 중 **완독일에 `required` 가 걸려 있다.** 접힌 `<details>` 안의
`required` 가 빈 값이면 브라우저는 *"An invalid form control with name='' is not focusable"*
로 제출을 **조용히 막는다.** 화면에는 아무 에러도 보이지 않는다 — 60초 의식이 이유 없이
실패하는 최악의 형태다.

처리:
- 완독일 `Input` 에서 `required` 제거
- `Label` 의 `*` 표시도 제거 (접힌 안에 숨은 필수는 거짓 표시다)
- `handleSubmit` 에서 `status === 'completed'` 이고 `completedDate` 가 빈 문자열이면
  오늘 날짜로 채운다

기본값이 이미 오늘이므로 이 폴백은 **사용자가 의도적으로 날짜를 비운 경우**에만 동작한다.
완독 기록이라는 맥락에서 그때 "오늘"로 보는 것이 자연스럽다.

독서 상태의 `required` 는 보이는 자리에 남으므로 그대로 둔다.

### B2. 저장 후 즉시 결과

`app/(protected)/books/add/page.tsx` 는 현재 저장 성공 시 `toast.success` 하나를 띄우고
`router.push('/books')` 로 서재 목록으로 보낸다. 사용자가 방금 쓴 문장은 화면에서 사라진다.

**단계를 하나 더 둔다.** 그 페이지는 이미 `selectedBook` state 로 검색↔폼을 전환하므로,
같은 방식으로 세 번째 단계(완료)를 더한다. 라우트를 늘리지 않는다.

```
검색 → 등록 폼 → 완료 카드
```

새 컴포넌트 `apps/page0127/src/features/book/ui/BookSavedCard.tsx` 가 결과를 그린다.
담을 것은 네 가지이고, 그 이상 넣지 않는다:

| 자리 | 내용 |
| --- | --- |
| 확인 | 완독 1권이면 "첫 번째 책이 책장에 꽂혔어요", 그 외 "N번째 책이 책장에 꽂혔어요". `read_count > 1` 이면 재독 문구 |
| 되돌려주기 | 사용자가 쓴 한줄평을 인용해 보여준다 — **이 트랙의 핵심**이고 제품 약속의 증거다. 한줄평이 없으면 이 블록을 숨긴다 |
| 강조 | `isLifeBook(rating)` 이면 인생책 표기 (트랙 A의 `@/entities/book` 헬퍼를 쓴다) |
| 다음 행동 | `내 책장 보기` (→ `/books`) · `한 권 더 기록` (→ 검색 단계로 초기화) |

**완독일 때만 결과 카드를 보여준다.** `읽고싶어요`·`읽는 중` 으로 저장한 경우는 기존처럼
`/books` 로 이동한다. "책장에 꽂혔어요" 가 거짓이 되고, 어색한 대체 문구를 새로 만들
이유가 없다.

**완독 권수 조회:** 저장 직후 `count: 'exact', head: true` 쿼리 한 개로 사용자의 완독
권수를 얻는다. `status = 'completed'` 로 필터한다. **새 API 라우트를 만들지 않고** 이
페이지가 이미 쓰는 브라우저 Supabase 클라이언트 경로(`features/book/api`)를 쓴다.

이 쿼리가 실패해도 결과 카드는 떠야 한다 — 권수 없이 "책장에 꽂혔어요" 만 보여주고,
`error` 는 `console.warn` 으로 남긴다. 트랙 A에서 정한 방침이다(Supabase 클라이언트에
`Database` 제네릭이 없어 런타임 `error` 가 유일한 신호다).

**기존 동작 중 유지할 것:** 책등 이미지 백그라운드 검증(`validateSpineImageUrl` →
`updateBook`)은 등록을 막지 않도록 결과를 기다리지 않는다. 결과 단계로 전환해도 이
백그라운드 작업은 그대로 돌아야 한다.

### B3. 취향 분석 진입 문구

`apps/page0127/src/widgets/public-library/PublicLibraryHeader.tsx` 의 진입 토스트가
"취향 분석을 위해 최소 5권의 완독한 책(별점 포함)이 필요합니다." 로 부정형이다.
리뷰의 권고("1/5 같은 표현 대신 긍정적으로")에 따라 바꾼다. 확정 문구:

```
별점을 남긴 완독 책이 ${5 - analyzableBookCount}권 더 모이면 취향 분석을 볼 수 있어요.
```

`analyzableBookCount` 는 이 컴포넌트가 이미 prop 으로 받고 있으므로 추가 조회가 없다.
"필요합니다"(요건)에서 "볼 수 있어요"(가까워진 보상)로 바뀌는 것이 요점이다.

재분석 토스트("이전 분석 이후 새로 읽은 책이 N권이에요. 5권 이상 쌓이면 다시 분석할 수
있어요.")는 이미 남은 양을 알려주는 긍정형이므로 **그대로 둔다.**

**5권 게이트 자체는 바꾸지 않는다.** AI 호출 비용과 묶인 제품 결정이고, 리뷰도 AI 분석은
5권째의 큰 보상으로 남기라고 했다. 이 트랙이 더하는 것은 1~4권 구간의 작은 보상(B2)이다.

## 테스트

이 트랙이 건드리는 것은 전부 프레젠테이션 계층이고, 저장소에는 React 컴포넌트 테스트
하네스가 없다(`vitest` 는 순수 함수만, Playwright 는 `e2e/*.spec.ts`). 따라서:

**단위 테스트 (vitest):** 순수 함수로 뽑을 수 있는 것 하나만 테스트한다 —
결과 카드의 확인 문구를 만드는 함수. 예: `(completedCount, readCount) => string`.
케이스: 1권 → "첫 번째", 3권 → "3번째", `readCount = 2` → 재독 문구.
컴포넌트에서 문구 생성 로직을 분리하는 것이 목적이고, 그래야 카피 변경이 테스트로 잠긴다.

**수동 검증 (사용자):**
- 신규 등록에서 완독 선택 시 보이는 결정이 3개인지 (상태·한 문장·평가)
- `더 남기기` 를 펼치지 않고 저장이 되는지
- **완독일을 비우고 접은 채 저장** — 조용히 막히지 않고 오늘로 저장되는지 (`required` 회귀 검사)
- 저장 후 결과 카드에 내가 쓴 한줄평이 인용되는지
- 인생책으로 저장하면 인생책 표기가 나오는지
- `한 권 더 기록` 이 검색 단계로 돌아가는지
- 읽고싶어요로 저장하면 결과 카드 없이 서재로 가는지
- 수정 화면은 `더 남기기` 가 펼쳐진 상태로 열리는지

로컬 Supabase 가 필요하다. 형제 worktree 가 같은 로컬 DB 를 공유하므로 로컬 스키마가
main 과 다를 수 있다는 점을 감안한다.

## 커밋 단위

1. **B1 폼 승격·접기 + 완독일 `required` 제거** — 1파일, ~80줄
2. **B2 결과 단계 + `BookSavedCard`** — `add/page.tsx` + 새 컴포넌트 + 문구 함수와 테스트, ~150줄
3. **B3 취향 분석 문구** — 1파일, ~5줄

## 이번 범위에서 제외 (명시)

- **카테고리 "결" 표시** ("이번 책으로 '관계·성장' 결이 추가됐어요") — 신규 결인지
  판정하려면 기존 카테고리 집합 조회가 추가로 필요하고, 2번째 에세이인데 "에세이 결이
  더해졌어요" 라고 하면 거짓이 된다. 문구 정확성이 확보될 때 다시 본다.
- **공유 카드 이미지·사용자별 동적 OG** — 트랙 E. B2 의 결과 카드는 앱 안에서만 보인다.
  그래서 결과를 라우트가 아닌 페이지 내 단계로 뒀다 — 공유 링크가 필요해지는 시점이
  트랙 E이고, 그때 라우트로 올린다.
- **활성화·재방문 계측** — 트랙 D. "가입 후 24시간 안에 첫 책과 한줄 생각을 남긴 사용자"
  라는 활성화 기준은 D에서 측정한다. 이 트랙은 이벤트를 심지 않는다.
- **주간 회상 메일·알림** — 트랙 C
- **취향 분석 5권 게이트 조정** — 제품 결정, 유지
- 등록 폼을 신규·수정 두 컴포넌트로 분리하는 리팩터링 — prop 한 개로 해결되므로 불필요
