# 트랙 C — 주간 회상 "이번 주의 한 장"

작성일: 2026-07-28 브랜치: `track-c-weekly-recap` (베이스: `main` = `658d332`)

## 배경

외부 제품 리뷰를 6개 트랙으로 쪼갠 것 중 네 번째 라운드다. 트랙 A(`cca03be`)는 숫자가 틀리지 않게
했고, 트랙 B(`e759127`)는 기록 경험을 1분 의식으로 만들었다. 트랙 C는 **사람이 다시 오게 만드는**
쪽이다.

트랙 A 문서에는 "재방문 구조 (주간 회상)" 한 줄, 트랙 B 문서에는 "주간 회상 메일·알림"으로만 미뤄져
있었다. 무엇을 만들지는 정해진 바 없었고, 이 문서가 그것을 정한다.

### 착수 전 실측이 설계를 뒤집었다

"주간 회상"이라는 말에서 가장 먼저 떠오르는 건 *이번 주에 읽은 책 요약*이다. 운영 DB를 읽어보니 그
안이 제일 나빴다.

운영 공개 데이터 실측 (2026-07-28, 공개 책 157권 · 사용자 2명):

| 후보 카드        | 소재 실측                                                                              | 판정                 |
| ---------------- | -------------------------------------------------------------------------------------- | -------------------- |
| 이번 주의 나     | **최근 52주 중 33주가 완독 0건** (63%)                                                 | 3주 중 2주는 빈 화면 |
| 그 해 이 주의 나 | 완독일이 2023-01~2026-07 **42개월**에 분포. 1년 전 이 주 3건 · 2년 전 2건 · 3년 전 4건 | **거의 매주 걸린다** |
| 잠든 책          | `status` = completed 155 · reading 2 · **want_to_read 0**                              | 소재 2권             |
| 남들의 반응      | 좋아요 0 · 팔로우 0 · 댓글 1                                                           | 소재 없음            |

원인이 결정적이다. **등록일(`created_at`)은 2026-07에 156권이 몰려 있는데, 완독일
(`completed_date`)은 3년 반에 걸쳐 퍼져 있다.** 이 서비스는 실제로 _"지금 읽는 걸 기록하는 곳"이
아니라 "지금까지 읽은 걸 옮겨 담는 곳"_ 으로 쓰이고 있다.

그래서 데이터가 가장 두꺼운 곳은 **과거**다. 흔히 "과거 회상은 데이터가 쌓여야 가능하니 오픈 초기엔
못 한다"고 보지만, 이 서비스는 정반대다.

### 서비스 성격에 대한 합의

사용자 확인 결과, 이 패턴은 **순서**로 이해하기로 했다 — 가입 초기에는 과거 이력을 옮겨 담는
아카이브로 쓰이고, 그다음부터 현재 기록으로 넘어간다. 회상은 두 단계 모두에서 작동해야 하므로, 한
종류의 카드가 아니라 **사용자 상태에 따라 다른 카드를 고르는 구조**가 된다.

## 목표

로그인한 사용자가 홈에 왔을 때 **이번 주에 할 말이 있는 카드 1장**을 만난다. 그 1장은 매주 바뀐다.

### 비목표 (이번 범위 아님)

- 밖에 있는 사람을 끌어오는 것. 인앱 카드는 **이미 들어온 사람에게만** 보인다. 목표를 글자 그대로
  달성하려면 메일·푸시가 필요하고, 그건 이번 범위가 아니다(§ 결정 1).
- 재방문율 계측. 트랙 D 영역이고, D-1이 별도 브랜치에서 방문 이력을 심는 중이다.

## 결정 1 — 채널: 인앱만

메일 인프라는 **0건**이다(`resend`·`nodemailer` 등 의존성 없음). 인앱 알림 인프라는 이미 완비돼
있다(`notifications` 테이블 + 실시간 + 드롭다운 + 배지).

메일까지 한 번에 가면 도메인 인증·수신거부·발송 로그·개인정보처리방침 갱신이 따라붙어 트랙 C의
절반이 "발송 인프라 구축"이 된다. **지금 검증해야 할 것은 "회상 화면이 볼 만한가" 하나** 이므로,
이번 라운드는 화면까지만 만든다.

인앱 알림(`notifications`)으로 보내는 것도 이번 범위에서 뺀다. 회상은 **행위자가 없는 시스템
알림**인데, 현재 스키마는 그걸 못 받는다:

```sql
type    TEXT NOT NULL CHECK (type IN ('follow', 'comment', 'like')),
actor_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
```

`type` CHECK 확장 + `actor_id` nullable화 + `NotificationItem`의 actor 전제 렌더 분기까지 기존 알림
시스템 전체를 건드리는 일이 되고, **지금 그 알림을 받을 사람이 0명**이다.

## 결정 2 — 생성 시점: 열 때 계산, 저장 없음

테이블도 크론도 만들지 않는다. 사용자가 홈을 열 때 그 자리에서 계산한다.

근거는 트랙 D-1 문서가 이미 세운 기준이다 — _"나중에 소급 계산되는 건 나중에 만들고, 오늘 안 심으면
영영 못 되살리는 것만 지금 심는다."_

회상은 **100% 소급 가능하다.** 내용이 전부 `books.completed_date` 같은 이미 있는 데이터에서
계산되므로, "지난 회상 아카이브"를 반년 뒤에 만들어도 지난 반년 치가 그대로 복원된다. 지금
서랍(테이블)을 만들어 둘 이유가 없다.

반대로 크론+저장의 비용은 지금 발생한다(테이블 + 크론 + 위의 알림 스키마 개조).

참고: Vercel Hobby 플랜의 크론 제약은 **프로젝트당 100개, 하루 1회보다 잦으면 불가, ±59분 오차**다.
주간 크론 자체는 문제가 없었다 — 이번에 안 쓰는 이유는 플랜 제약이 아니라 위의 소급 가능성 때문이다.

## 결정 3 — 카드 1장과 침묵 규칙

**1장만 보여준다.** 여러 장을 늘어놓는 순간 "주간 요약 대시보드"가 되고 빈 슬롯이 생긴다. 실측상
어떤 주는 채울 게 1종류뿐이다. 1장이면 항상 꽉 찬 화면이 나온다. 회상은 훑는 것이 아니라 한 번
멈추는 경험이므로 형식에도 맞다.

### 카드 3종과 고정 우선순위

위에서부터 처음 걸리는 것 하나를 쓴다.

| 순위 | 카드                  | 조건                                                           |
| ---- | --------------------- | -------------------------------------------------------------- |
| 1    | **이번 주의 나**      | 이번 주(KST 월~일)에 `completed_date` 또는 `created_at`이 있다 |
| 2    | **그 해, 이 주의 나** | n년 전 같은 주에 완독한 책이 있다                              |
| 3    | **아직 읽는 중**      | `status = 'reading'` 인 책이 있다                              |
| —    | (없음)                | 위 셋 다 해당 없음 → **`null`. 카드를 그리지 않는다**          |

**표의 마지막 줄이 이 설계의 핵심이다.** 억지로 채우면 _"이번 주 0권 완독"_ 같은 문구가 나오는데,
`00_docs/00_남은_작업_목록.md`가 이를 명시적으로 금지하고 있다. **할 말이 없으면 침묵한다.**

**1번 카드의 판정 기준에서 "한줄생각"은 뺐다.** `one_line_review`는 `books`의 칸일 뿐 작성 시각이
따로 없다. `updated_at`은 아무 수정에도 바뀌므로 "이번 주에 한줄생각을 남겼다"를 판정할 수 없다.
트랙 B가 한줄생각을 기록 의식의 핵심으로 만들었으므로 언젠가 시각 칸이 필요하겠지만, **그건 이
스펙의 범위가 아니다.**

1번 카드는 이번 주에 일어난 일에 따라 문구가 갈린다. 규칙을 못박는다:

| 이번 주에 있었던 일     | 문구                                                |
| ----------------------- | --------------------------------------------------- |
| 완독이 있다             | "이번 주에 N권을 끝내셨어요" (완독한 책을 보여준다) |
| 등록만 있고 완독은 없다 | "이번 주에 N권을 담으셨어요" (담은 책을 보여준다)   |

완독과 등록이 둘 다 있으면 **완독을 보여준다.** 끝낸 것이 담은 것보다 회상할 거리가 크다.

우선순위가 고정이므로 무작위가 없고, 같은 주에 홈을 몇 번 새로고침해도 같은 카드가 나온다. 후보가
여러 권일 때의 선택도 결정론으로 못박는다:

- **2번 카드** — ① 가장 최근 해부터 본다(1년 전 → 2년 전 → …). 걸리는 해가 나오면 거기서 멈춘다. ②
  그 해 안에서 **기념일(오늘의 월·일)에 완독일이 가장 가까운 책**을 대표로 쓰고, 나머지는 "같은 주에
  N권 더"로 붙인다. ③ 날짜 차이까지 같으면 `id` 오름차순.
- **1번 카드** — 완독일(없으면 등록일)이 **가장 최근**인 책이 대표. 같으면 `id` 오름차순.
- **3번 카드** — `created_at`이 **가장 오래된** 읽는 중인 책. 가장 오래 방치된 것이 회상할 거리가
  크다. 같으면 `id` 오름차순.

`id` 오름차순 꼬리표는 장식이 아니다. 이게 없으면 DB가 돌려주는 행 순서에 결과가 좌우돼 "같은 입력 →
같은 출력"이 깨진다(§ 검증의 7·8번).

### "다 도입"이 여기서 성립한다

1번 카드만 있으면 3주 중 2주는 화면이 사라지지만, 2번이 받쳐주면 사실상 매주 뭔가가 뜬다. 그리고 두
카드가 § 배경의 "가입 초기엔 아카이브, 그다음엔 현재 기록"이라는 순서를 그대로 구현한다 — 신규
사용자는 과거 이력을 몰아 넣었으니 2번이 걸리고, 활동이 붙으면 1번이 이긴다.

**"남들의 반응" 카드는 넣지 않는다.** 실측 소재가 0·0·1건이라 몇 달간 렌더 결과가 항상 빈 상태이고,
**눈으로 검증할 방법이 없다.** 우선순위 표에 한 줄 추가하는 일이므로 소재가 생긴 뒤에 붙인다.

그대로다.

## 구조

핵심은 함수 하나다.

```
selectRecapCard(books, now) → RecapCard | null
```

책 목록과 기준 시각을 넣으면 어떤 카드를 그릴지가 나온다. DB도 화면도 모르는 **순수 함수**다.

떼어놓는 이유 셋:

1. **지금 테스트할 수 있다.** "작년 이맘때 책이 없는 사용자"를 화면으로 재현하려면 계정을 새로
   만들어야 하지만, 테스트로는 한 줄이다.
2. **나중에 메일을 붙일 때 그대로 쓴다.** 메일 본문도 "어떤 카드냐"만 알면 된다.
3. **결정론이 코드에 드러난다.** 입력이 같으면 출력이 같다는 걸 테스트로 못박는다.

### 파일

| 파일                                             | 하는 일          |

FSD 구조와 파일명은 주변 코드를 따른다(`entities/<name>/{model,lib,api}`, `widgets/<name>/ui`).

### 패키지화 검토

`CLAUDE.md` 5번 규칙(패키지화 우선 검토)에 따라 확인했다. `selectRecapCard`는 순수 함수라
후보이지만, **입력 타입이 이 앱의 `books` 스키마에 묶여 있어 재사용처가 없다.** 앱 안
`entities/recap`에 두고, 나중에 메일 발송이 별도 서비스로 갈라질 때 빼는 것이 맞다.

### 데이터 조회

내 책을 한 번에 읽어 함수에 넘긴다. 필요한 칸만 고른다 —
`id, title, author, cover_image, status, completed_date, created_at, rating, one_line_review`.

`description`·`toc` 같은 큰 칸은 **선택하지 않는다**(`select('*')` 금지). 157권 기준 약 30KB다.

이 방식은 책이 아주 많아지면 무거워진다. **한 사람이 2000권을 넘으면 DB 쪽 계산(RPC)으로 옮긴다**를
함수 주석에 남긴다.

### 주 경계는 KST

"이번 주"는 **한국 시간 월요일 00:00 ~ 일요일 24:00**이다. 서버는 UTC로 돌기 때문에 UTC로 자르면
한국 시각 밤 9시 이후의 일이 다음 날로 밀린다.

D-1 브랜치가 이미 `toKstDateKey`(`src/shared/lib/date.ts`)를 만들어 뒀다. **그 커밋 2개만
cherry-pick해서 가져온다**(§ 진행 순서).

## 진행 순서

트랙 C 브랜치는 **`main`에서** 딴다. D-1을 기다리지 않는다 — D-1은 미완성이고 아래 § 부록의
마이그레이션 충돌을 안고 있어서, 거기에 묶이면 트랙 C도 병합할 수 없게 된다.

D-1의 KST 유틸 커밋 2개(`61e7a89`, `41bd6de`)는 `src/shared/lib/date.ts`와 그 테스트 **두 파일만**
건드리며 마이그레이션과 무관하다. cherry-pick으로 가져오면, 나중에 D-1이 `main` 위로 rebase될 때
git이 같은 변경으로 알아보고 흡수한다. **두 트랙이 서로를 막지 않는다.**

9번이 KST 유틸이 필요한 진짜 이유다. 7·8번은 § 결정 3의 결정론 규칙을 지킨다.

**9번의 시각은 아무 일요일 밤이나 되는 게 아니다.** KST는 UTC보다 9시간 빠르므로, 둘이 날짜를 다르게
보는 구간은 **UTC 15:00~24:00** 뿐이다. 예컨대 "KST 일요일 밤 11시"는 UTC로도 일요일 14시라 **UTC로
잘못 짠 코드도 통과한다** — 검증이 되지 않는다. UTC 일요일 16:00을 쓰는 이유는 그 시각에 UTC는 "아직
지난 주", KST는 "이미 새 주"로 갈라지기 때문이다.

## 이 스펙이 만들지 않는 것

- **메일 발송** — 인프라 신설이 필요하다. `selectRecapCard`를 순수 함수로 떼어놨으므로 붙일 때 생성
  로직을 그대로 재사용한다.
- **인앱 알림 보내기** — `notifications`의 `actor_id NOT NULL`·`type` CHECK 개조가 선행돼야 한다(§
  결정 1).
- **지난 회상 아카이브** — 소급 계산이 가능하므로 나중에 만들어도 잃는 게 없다(§ 결정 2).
- **NEW 배지** — 브라우저에 "마지막으로 본 주"를 기억시켜야 해서 기기를 바꾸면 틀어진다. 카드가 매주
  다른 책 표지로 통째로 바뀌므로 이미 눈에 띈다. 메일을 붙일 때 함께 다룬다.
- **"남들의 반응" 카드** — 소재 0건이라 검증 불가(§ 결정 3).
- **한줄생각 작성 시각 칸** — 지금은 언제 썼는지 알 방법이 없어 1번 카드의 판정에서 뺐다 (§ 결정 3).
  칸을 추가하는 것은 스키마 변경이라 별도 건이다.
- **평점 체계 정리** — `rating = 10`이 12건 남아 있는 것은 트랙 F 범위다.
- **방문 이력 적재 / 재방문율 계측** — 트랙 D.

## 부록 — D-1 마이그레이션 번호 충돌 (트랙 C와 별건)

트랙 C와 무관하지만 **D-1을 병합하기 전에 반드시 고쳐야 한다.** 여기 적어 두는 이유는 이 문제 때문에
트랙 C의 진행 순서가 바뀌었기 때문이다.

```
main       : 20260728000002_drop_activity_notifications.sql
D-1 브랜치 : 20260728000002_create_user_daily_visits.sql      ← 같은 번호
             20260728000003_drop_activity_notifications.sql   ← 이쪽으로 밀어놨음
```

D-1은 main의 번호 수정(`73fd220`)보다 먼저 분기(`037c32d`)했고, 같은 파일을 각자 다른 번호로 밀었다.

**운영 DB에 `20260728000002`가 이미 적용돼 있다** (`npx supabase migration list`로 확인, 기록 시각
2026-07-28 00:00:02, linked project = `sjngwxtykqhlsvxcyqah` = 운영).

그래서 D-1을 이대로 병합하면:

- `20260728000002_create_user_daily_visits.sql` → 해당 버전이 이미 `schema_migrations`에 있으므로
  **조용히 건너뛴다. 테이블이 안 생긴다.**
- `20260728000003_drop_activity_notifications.sql` → 새 버전이라 다시 실행된다(DELETE라 무해).

**에러가 나지 않는다는 점이 위험하다.** 마이그레이션은 성공했다고 나오는데 `/api/visit`가 런타임에
터진다.

고치는 방법:

```
D-1 브랜치에서
  20260728000003_drop_activity_notifications.sql   → 삭제 (main 것을 쓴다)
  20260728000002_create_user_daily_visits.sql      → 20260728000003_ 로 개명
```

2026-07-28 시점에 D-1은 다른 세션이 작업 중이며(`e5a1077`), 충돌은 아직 남아 있다.
