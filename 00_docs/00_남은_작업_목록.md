## ✅ 1순위 — 고장을 고장으로 알아채기 (2026-07-29 완료)

**2026-07-29에 이 문제가 실제로 사고를 냈다.** 트랙 F 코드는 배포됐는데 운영 DB에 마이그레이션이 안
올라가서, `books.is_life_book` 을 쓰는 조회가 전부 `42703 column does not exist` 로 죽고 있었다.
그런데 **모든 페이지가 HTTP 200 이었다.** 운영 DB에 직접 쿼리를 던져보고서야 발견했다.

기능이 아무리 많아도 고장을 못 보면 베타를 열 수 없다. 그래서 이게 맨 위다.

- [x] **앱이 DB 에러를 삼킨다** — **의도된 graceful degradation 으로 판정**(2026-07-29). 화면이
      안 깨지는 건 그대로 두고 **감시 쪽을 고쳤다**. 조회 실패 18곳의 `console.error` 도 유지.
- [x] **배포 코드와 운영 스키마가 어긋난 걸 아무도 모른다** — `/api/health` 가 **스키마 계약**까지
      확인한다(`app/api/_helpers/schemaContract.ts`). 위반 시 503 + 무엇이 깨지는지 함께 반환하고,
      `uptime.yml` 이 주기적으로 부르므로 자동으로 알림이 온다(설정은 5분이지만 실측 3~6시간 —
      2순위 참고). **CI 가 아니라 운영 안에서 도는 이유:**
      CI 는 운영 DB를 못 본다(`check:non-production-db` 가드). health 는 이미 운영 자격증명으로
      돌아 **새 secret 이 필요 없다.**
      ⚠️ **마이그레이션으로 컬럼을 추가하고 코드가 그걸 읽기 시작하면 `SCHEMA_CONTRACT` 에 한 줄
      넣어야 한다.** 자동이 아니다.
- [x] **CI secrets 검사가 값의 유효성을 안 본다** — `scripts/assert-supabase-reachable.mjs` 가
      `/rest/v1/` 를 1회 호출해 **키가 실제로 먹히는지** 확인한다. 401/403 이면 CI 가 실패한다.

> **사고를 로컬에서 재현해 확인했다** — `books.is_life_book` 을 지우니 화면은 전부 200 인데
> `/api/health` 만 503 이 됐다. 자세한 내용은
> `docs/superpowers/specs/2026-07-29-fail-loud-schema-drift.md`.
