## 🚨 1순위 — 고장을 고장으로 알아채기

**2026-07-29에 이 문제가 실제로 사고를 냈다.** 트랙 F 코드는 배포됐는데 운영 DB에 마이그레이션이 안
올라가서, `books.is_life_book` 을 쓰는 조회가 전부 `42703 column does not exist` 로 죽고 있었다.
그런데 **모든 페이지가 HTTP 200 이었다.** 운영 DB에 직접 쿼리를 던져보고서야 발견했다.

기능이 아무리 많아도 고장을 못 보면 베타를 열 수 없다. 그래서 이게 맨 위다.

- [ ] **앱이 DB 에러를 삼킨다** — 조회가 실패해도 로그만 남기고 렌더를 계속한다
      (`[banner] 슬라이드 조회 실패`, `레이트 리밋 체크 실패 (요청은 통과시킴)`). CI에서 Supabase
      키가 무효라 DB에 전혀 못 닿는 상태였는데도 E2E 8개 중 **7개가 통과**했고, `/api/health` 만
      503을 냈다. → 의도된 graceful degradation 인지 먼저 판단하고, 맞다면 **스모크가 DB 이상을
      잡도록** 별도 보강.
- [ ] **배포 코드와 운영 스키마가 어긋난 걸 아무도 모른다** — 위 사고의 직접 원인. main 에 있는
      마이그레이션이 운영에 다 적용됐는지 확인하는 단계가 어디에도 없다. →
      `npx supabase migration list` 로 local/remote 차이를 CI 나 배포 후 점검에서 확인. **미적용이
      있으면 눈에 띄게 실패시킨다.**
- [ ] **CI secrets 검사가 값의 유효성을 안 본다** — `ci.yml` 의 `Check Supabase secrets present` 가
      **존재 여부(빈 문자열)만** 확인해서, 키가 무효인 3일 내내 "secrets 정상"으로 표시됐다 (실제
      원인은 URL·키가 서로 다른 프로젝트 것). → `/rest/v1/` 1회 호출로 **연결까지** 확인.

## 🟢 4순위 — 트랙 C(주간 회상) 후속

회상 카드는 완료·병합됐다(PR #31). 아래는 **의도적으로 뺀 것**이며, 뺀 이유가 각각 있다.

- [ ] **회상 메일 발송** — 인앱 카드는 이미 들어온 사람에게만 보인다. 밖에 있는 사람을 끌어오려면
      메일이 필요. 발송 서비스·도메인 인증·수신거부·개인정보처리방침 갱신이 딸려온다. **사용자 50명
      넘으면 착수**(2026-07-29 합의).
- [ ] **회상을 인앱 알림으로** — 현재 `notifications` 는 `actor_id NOT NULL` 이라 **행위자 없는
      시스템 알림**을 담지 못한다. `type` CHECK 확장 + `actor_id` nullable + `NotificationItem` 의
      actor 전제 렌더 분기가 필요. 종 아이콘 인프라는 이미 있으므로 **셋 중 가장 싸다.**
- [ ] **지난 회상 아카이브** — 회상은 100% 소급 계산되므로 나중에 만들어도 그때까지가 다 복원된다.
      급하지 않다.
- [ ] **"남들의 반응" 카드** — 좋아요·팔로우·댓글 소재가 0·0·1건이라 만들어도 화면이 계속 비어
      **제대로 만들었는지 확인할 수 없다.** 사람이 모인 뒤.
