# 기술 스택 가이드

> 선택한 기술과 그 이유

---

## Frontend

### Next.js 16 (App Router)

**선택 이유:**

- ✅ React 기반 풀스택 프레임워크 (API Route로 외부 API·DB 호출을 서버에 둠)
- ✅ App Router로 최신 패턴 학습
- ✅ SSR/SSG로 SEO 최적화
- ✅ Vercel 배포 최적화
- ✅ React 19 지원

**대안:**

- ❌ Vite + React: CSR만 지원

### TypeScript

**선택 이유:**

- ✅ 타입 안정성
- ✅ IDE 자동완성
- ✅ 리팩토링 용이

### Tailwind CSS v4 + shadcn/ui

**선택 이유:**

- ✅ 유틸리티 우선 CSS
- ✅ shadcn/ui로 빠른 UI 구축
- ✅ 컴포넌트 코드를 직접 소유해 커스터마이징 쉬움

**대안:**

- ❌ MUI: 무겁고 커스터마이징 어려움
- ❌ Styled-components: 런타임 오버헤드

### TanStack Query (서버 상태)

**선택 이유:**

- ✅ 서버 상태 관리 최적
- ✅ 캐싱, 리페칭 자동화
- ✅ 낙관적 업데이트 지원

로그인 사용자도 Query로 가져와 Context 하나로 트리에 공급한다.

### React Context (클라이언트 전역 상태)

Zustand 같은 상태 관리 라이브러리는 쓰지 않는다.

**이유:**

- ✅ 서버 상태를 TanStack Query로 분리하고 나니 여러 라우트가 공유하는 클라이언트 상태가 로그인 사용자 하나뿐
- ✅ 그 값은 거의 바뀌지 않아 Context로 충분

**도입 기준:** 여러 라우트가 함께 쓰고 자주 바뀌는 클라이언트 상태가 생기면 Zustand(selector로 필요한 조각만 구독)를 검토

### axios

**선택 이유:**

- ✅ 인터셉터로 공통 로직 처리 (인증, 에러 핸들링)
- ✅ API 엔드포인트 중앙 관리 (`endpoints.ts`)
- ✅ Query Key는 엔티티별 `queryKeys.ts`로 관리

**대안:**

- ❌ fetch: 인터셉터 없음, 보일러플레이트 많음
- ❌ 클라이언트에서 Supabase SDK 직접 사용: DB 종속성 높음

**아키텍처:**

```
Frontend (Client Component)
    ↓ axios
API Routes (Next.js)
    ↓ Supabase SDK
Supabase (PostgreSQL)
```

## Backend & Database

### Supabase

**선택 이유:**

- ✅ PostgreSQL + Auth + Storage 통합
- ✅ 무료 티어 충분
- ✅ Next.js 통합 쉬움
- ✅ Realtime 기능 (알림용)

**대안:**

- ❌ Firebase: NoSQL 제약
- ❌ PlanetScale: Auth 별도 구현 필요

### YES24 도서 API

**선택 이유:**

- ✅ 알라딘 OpenAPI 종료(2026-10-30 예정)에 대비해 YES24로 전환
- ✅ 서버 라우트에서만 호출하고 응답을 캐시

공급자는 `getBookProvider()` 한 곳 뒤에 숨겨 두어, 다음 교체도 이 함수만 바꾸면 된다.

## AI

### OpenAI API (gpt-4o)

**선택 이유:**

- ✅ 강력한 텍스트 분석
- ✅ JSON 모드 지원
- ✅ 이미지 생성 기능을 붙일 경우 한 공급자로 텍스트·이미지를 모두 처리 가능

`gpt-4o-mini`로 시작했다가 취향 분석·궁합 분석의 문장 품질 때문에 `gpt-4o`로 올렸다. 분석 1건당 호출이 1번이라 비용 차이가 작다.

**대안:**

- Claude: 동급 모델(Sonnet 5.5) 가격이 비슷해 비용은 결정 요인이 아님. 한국어 결과 품질은 직접 비교 후 판단

## 🏗️ 아키텍처 패턴

### FSD (Feature-Sliced Design)

**레이어 구조:**

```
app/      → 라우팅, 페이지
widgets/  → 복합 컴포넌트 (Header 등)
features/ → 기능 단위 (auth, book 등)
entities/ → 비즈니스 엔티티 (book, user 등)
shared/   → 공통 UI, 설정, 유틸
```

**선택 이유:**

- ✅ 명확한 의존성 규칙
- ✅ 확장 가능한 구조
- ✅ 팀 협업에 유리
