### TypeScript

- ✅ 리팩토링 용이

### Tailwind CSS v4 + shadcn/ui

**선택 이유:**

- ✅ 유틸리티 우선 CSS
- ✅ Tailwind v4: 성능 개선, PostCSS 기반
- ✅ shadcn/ui로 빠른 UI 구축

### React Query (TanStack Query)

**선택 이유:**

- ✅ 서버 상태 관리 최적
- ✅ 캐싱, 리페칭 자동화
- ✅ 낙관적 업데이트 지원

**현재 사용:**
- 도입 완료 (`@tanstack/react-query` v5)
- axios와 함께 사용하여 서버 상태 관리
- 로그인 사용자도 `useCurrentUser`(Query)로 가져와 `CurrentUserProvider`(Context)로 트리에 공급

### 클라이언트 전역 상태: Context (Zustand 미도입)

**현재 상태:**

- Zustand는 설치돼 있지 않음 (`apps/page0127/package.json`에 없음)
- 클라이언트 전역 상태는 `CurrentUserProvider`(React Context) 하나뿐
  - 위치: `src/entities/user/providers/CurrentUserProvider.tsx`
- 서버 상태는 React Query가 담당하므로 Context에는 Query 결과만 얹음

**도입하지 않은 이유:** (⚠️ HJ 확인 필요)

- 서버 상태를 React Query로 분리하고 나니 여러 라우트가 공유하는 클라이언트 상태가 사실상 없음
- prop drilling 통증이 아직 없어 Context로 충분, 필요해지면 그때 도입
- 근거: `00_react_study/phase3_day38_상태구조설계.md`의 "Zustand 도입 결정 — 현재로선 No"

### axios

**선택 이유:**

- ✅ RESTful API 호출에 최적화
- ✅ 인터셉터로 공통 로직 처리 (인증, 에러 핸들링)
- ✅ TypeScript 지원 우수
- ✅ 요청/응답 변환 자동화
- ✅ API 엔드포인트 중앙 관리 (endpoints.ts)
- ✅ Query Key 중앙 관리 (queryKeys.ts)

**대안:**

- ❌ fetch: 인터셉터 없음, 보일러플레이트 많음
- ❌ Supabase SDK 직접 사용: DB 종속성 높음

**아키텍처:**

```
Frontend (Client Component)
    ↓ axios
API Routes (Next.js)
    ↓ Supabase SDK
Supabase (PostgreSQL)
```

## 🏗️ 아키텍처 패턴

### FSD (Feature-Sliced Design)

**레이어 구조:**

```
app/      → 라우팅, 페이지
widgets/  → 복합 컴포넌트 (Header 등)
features/ → 기능 단위 (auth, book 등)
entities/ → 비즈니스 엔티티 (book, user 등)
shared/   → 공통 UI, 설정, 유틸
```

**선택 이유:**

- ✅ 명확한 의존성 규칙
- ✅ 확장 가능한 구조
- ✅ 팀 협업에 유리
