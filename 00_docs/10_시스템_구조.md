## ④ 데이터베이스 — 개념과 구조

Supabase 안에 든 것은 Postgres 데이터베이스다. 먼저 낱말 다섯 개만 알면 나머지가 읽힌다.

| 낱말 | 원말 | 뜻 |
| --- | --- | --- |
| **테이블(표)** | table | 엑셀 시트 한 장이라고 보면 된다. 이 프로젝트엔 표가 27장 있다. |
| **행과 열** | row / column | "홍길동이 2월 3일에 담은 책"이 한 행. 그 행 안의 제목·표지·별점이 각각 열. |
| **기본키 · 외래키** | primary / foreign key | 모든 행에는 겹치지 않는 `id`(uuid)가 붙는다. 다른 표의 id를 적어 두는 열이 외래키 — "이 댓글은 저 책의 것"을 잇는 실이다. |
| **RLS** | Row Level Security | 표마다 붙은 "누가 어느 행을 볼 수 있나" 규칙. 앱이 아니라 DB가 판정한다. 권한 없는 행은 에러가 아니라 그냥 안 보인다. |
| **마이그레이션** | migration | 표를 새로 만들거나 칸을 추가한 내역을 SQL 파일로 쌓아 둔 것. 순서대로 재생하면 어느 환경에서든 같은 모양이 된다. |

### 가장 중요한 관계 — "책"이 두 층으로 나뉘어 있다

```
profiles          1:N          books              N:1        global_books
(사람)         ──────────▶   (내 서재의 한 권)  ──────────▶  (세상의 책 한 권)
                              │
                              ├── book_comments      책 단위 댓글
                              ├── activities         담음·완독 같은 상태 변화
                              ├── book_record_likes  내 기록에 눌린 좋아요
                              └── book_thread_reads  어디까지 읽었는지 표시
```

| 표 | 무엇 한 줄이 한 행인가 |
| --- | --- |
| `profiles` | 가입한 사용자 한 명. 닉네임·아이디·공개 여부. |
| `books` | **내가 담은 책 한 권.** 같은 책을 다시 읽으면 행이 하나 더 생긴다(재독). |
| `global_books` | **ISBN 기준 책 원본.** 모든 사용자가 같은 행을 공유한다. 표지·저자·출간일. |

**왜 두 층으로 나눴나** — 표지·저자처럼 모두에게 똑같은 정보는 `global_books`에 한 번만 둔다. 별점·완독일처럼
사람마다 다른 것은 `books`에 둔다. 그래서 인생책 지정처럼 "책"에 대한 판단은 같은 책의 모든 회독에 함께
반영되고, 별점처럼 "그때의 나"에 대한 것은 회독마다 따로 남는다.

### 표 27장을 하는 일별로 묶으면

| 묶음 | 장수 | 테이블 | 하는 일 |
| --- | --- | --- | --- |
| 사람 | 2 | `profiles` `follows` | 가입자와 팔로우 관계 |
| 책 | 3 | `global_books` `books` `reading_records` | 책 원본과 내 서재의 기록. `reading_records`는 옛 호환용으로 거의 비어 있다 |
| 소셜·활동 | 6 | `activities` `book_comments` `book_record_likes` `book_likes` `book_thread_reads` `notifications` | 댓글·좋아요·활동 기록·알림 |
| AI | 5 | `taste_analyses` `book_recommendations` `mutual_recommendations` `compatibility_analyses` `ai_usage_logs` | 취향 분석 결과와 추천, 호출 비용 로그 |
| 운영 | 5 | `admin_actions` `hero_slides` `rate_limits` `book_ranking_snapshots` `user_daily_visits` | 어드민 감사 로그·배너·요청 제한·랭킹 스냅샷·방문 집계 |
| 품질 지표 | 3 | `quality_records` `quality_field_history` `quality_rum_samples` | 주간 측정치와 실제 사용자 체감 속도 |

**남아 있지만 더는 읽지 않는 표 3장** — `comments` · `activity_comments` · `activity_likes`. 댓글을 "활동"에
달던 옛 구조의 흔적이다. 책 단위로 옮기면서 읽기를 멈췄지만, 과거 데이터를 잃지 않으려고 표는 지우지 않았다.

## ⑤ 요청 하나가 흐르는 길 (그리고 두 개의 열쇠)

사용자가 버튼 하나를 누르면 아래 순서로 움직인다. 중요한 건 4번 — **권한 판정은 앱 코드가 아니라
데이터베이스가 한다.**

```
1. 브라우저
   사용자가 "책 담기"를 누른다
        ↓
2. Next.js 서버 (Vercel 위)
   Server Component가 직접 조회하거나, app/api/… 라우트 핸들러가 받는다
        ↓
3. Supabase 클라이언트
   쿠키에 든 로그인 토큰을 함께 실어 Supabase로 보낸다
        ↓
4. Postgres + RLS
   "이 사람이 이 행을 봐도 되나"를 DB가 행 단위로 판정한다
        ↓
5. 허용된 데이터만 돌아옴
   권한 없는 행은 에러가 아니라 그냥 "없는 것"처럼 빠진다
   → 그래서 조용히 0건이 되기도 한다
```

### 🔑 Supabase에 들어가는 열쇠는 두 개다

**anon key — 손님용 열쇠** (`NEXT_PUBLIC_SUPABASE_ANON_KEY`)

- 브라우저에 그대로 노출돼도 괜찮다. 이 열쇠로 뭘 하든 RLS 규칙이 항상 먼저 검사하기 때문이다.
- 남의 비공개 기록은 이 열쇠로 절대 못 본다.

**service_role key — 만능 열쇠** (`SUPABASE_SERVICE_ROLE_KEY`)

- RLS를 통째로 건너뛴다. 모든 사람의 모든 행을 읽고 지울 수 있다.
- 서버 코드(admin 기능·크론)에서만 쓰고, 브라우저로 새어 나가면 DB 전체가 열린 것과 같다.

> **기억할 규칙 하나** — `NEXT_PUBLIC_`이 붙는 순간, 그 값은 빌드 결과물에 문자 그대로 박혀 브라우저로
> 나간다. 비밀값에는 절대 붙이지 않는다.

> **⚠️ RLS를 믿으면 안 되는 구간** — 여러 사용자를 가로지르는 집계·랭킹 쿼리는 RLS가 알아서 걸러 준다고
> 가정하면 안 된다. `is_public` 같은 공개 조건을 쿼리에 직접 써야 한다.

## ⑥ DB 변경이 세 환경으로 퍼지는 길

DB의 구조는 손으로 고치지 않는다. `supabase/migrations/`에 SQL 파일을 시간순 번호로 쌓아 올리는 방식 —
**DB판 git**이라고 생각하면 된다. (2026-07-29 기준 47개)

```
1. SQL 파일을 쓴다
   supabase/migrations/20260729000001_life_book_per_book.sql
   앞 숫자는 만든 시각. 이 순서대로 실행된다.
        ↓
2. 로컬에서 검증
   supabase db reset
   빈 DB에서 47개를 처음부터 다시 실행한다. 중간에 깨지면 여기서 바로 드러난다.
        ↓
3. PR → CI
   GitHub Actions가 검사. 번호 중복 검사도 여기 들어 있다.
        ↓
4. 개발 Supabase
   main에 머지된 뒤 개발 프로젝트에 적용. Preview·CI가 이 DB를 본다.
        ↓
5. 운영 Supabase
   supabase db push — 수동으로 적용. 자동이 아니다. 사람이 판단해서 누른다.
```

### ⚠️ 함정 둘

**번호가 겹치면 조용히 무너진다**

- 같은 번호의 파일이 두 개면 `db reset`이 그 지점에서 멈추고, 그 뒤 파일은 전부 적용되지 않는다.
- 내 폴더만 보면 안 보인다. 새 파일을 만들기 전에 **`origin/main`의 마지막 번호**를 확인할 것.

**순서가 뒤집히면 화면이 깨진다**

- 코드가 먼저 배포되고 마이그레이션이 나중에 적용되면, 앱은 아직 없는 컬럼을 찾다가 실패한다.
- 원칙은 **DB 먼저, 코드 나중.**

## ⑦ CI/CD — 무엇이 저절로 되고, 무엇을 만들었나

사람이 손으로 하던 "검사"와 "배포"를 기계에게 넘긴 것. 두 글자를 나눠 보면 뜻이 분명해진다.

| | 원말 | 뜻 |
| --- | --- | --- |
| **CI** | Continuous Integration | **지속적 통합** — 코드를 합치기 전에 기계가 먼저 검사한다. 내 브랜치가 남의 코드와 만나도 깨지지 않는지 lint · 타입 · 테스트 · 빌드 · 브라우저 스모크를 PR마다 자동으로 돌린다. 하나라도 빨간불이면 머지 버튼이 막힌다. |
| **CD** | Continuous Deployment | **지속적 배포** — 합쳐지면 사람 손 없이 배포된다. FTP로 파일을 올리거나 서버에 접속할 일이 없다. main에 머지되는 순간 Vercel이 빌드해서 운영 주소에 갈아 끼운다. |

```
STEP 1              STEP 2            STEP 3 · 전부 자동        STEP 4 · 전부 자동
브랜치를 push  ──▶  PR을 연다  ──▶   검사 + Preview 배포  ──▶  머지 → 운영 배포
내가 하는 일은      이 순간 넷이       ✍️ Lint·Type·Build      넷 다 통과해야 머지 버튼이 열림
여기까지            동시에 깨어난다    ✍️ E2E smoke            main에 들어가는 순간 운영에 배포
                                      ⚡ Vercel 배포
                                      ⚡ Preview 코멘트

  🙋 이 줄 어디에도 마이그레이션은 없다 — DB 변경만은 사람이 supabase db push 를 눌러야 한다
```

### PR 하나를 열면 실제로 이 넷이 붙는다

| 체크 이름 | 누가 돌리나 | 어디에 적혀 있나 | 내가 만들었나 |
| --- | --- | --- | --- |
| Lint · Type-check · Build | GitHub Actions | `.github/workflows/ci.yml` | ✍️ 직접 작성 |
| E2E smoke (Playwright) | GitHub Actions | `.github/workflows/ci.yml` | ✍️ 직접 작성 |
| Vercel | Vercel | 레포에 파일 없음 | ⚡ 저절로 |
| Vercel Preview Comments | Vercel | 레포에 파일 없음 | ⚡ 저절로 |

### ⚡ Vercel을 붙이면 저절로 되는 것

GitHub 계정을 한 번 연결한 것 말고는 저장소에 아무 설정도 없다.

- PR을 열면 Preview 배포 + PR에 코멘트
- main에 머지되면 운영 배포
- 배포 상태를 GitHub 체크로 표시
- 이전 배포로 되돌리기(롤백)

> `vercel.json`은 Cron 같은 부가 기능용이지 **배포 자체와는 무관하다.** 그 파일을 지워도 배포는 계속된다.

### ✍️ 직접 만들어야 했던 것

아무도 대신 해 주지 않는다. 파일을 쓰고 커밋해야 돈다.

- `.github/workflows/ci.yml` — PR마다 lint · 타입 · 테스트 · 빌드 · E2E
- `.github/workflows/quality.yml` — 주 1회 품질 측정
- `.github/workflows/uptime.yml` — 5분마다 헬스체크
- `.github/dependabot.yml` — 주 1회 의존성 업데이트 PR (실행은 GitHub이 한다)
- Vercel 환경변수 · GitHub Secrets 등록
- main 브랜치 보호 규칙 (검사 통과 전 머지 금지)

> **⚠️ CD가 자동이라고 해서 DB까지 자동은 아니다** — 코드는 머지하는 순간 배포되지만, 마이그레이션은 사람이
> `supabase db push`를 눌러야 적용된다. 그래서 순서를 지켜야 한다: **DB 먼저, 코드 나중.** 반대로 하면 앱이
> 아직 없는 컬럼을 찾다가 깨진다.

## ⑧ 감시 — 문제를 알아채는 네 개의 눈

"안에서 보는 눈"과 "밖에서 보는 눈"을 따로 둔 이유가 있다. **앱이 완전히 죽으면 앱 안에 심어 둔 감시도
같이 죽어서** 아무도 알려 주지 못하기 때문이다.

### Sentry — 에러 보고 (앱 안에서 · 실시간)

- 서버와 브라우저에서 터진 예외를 자동으로 모은다. 서버의 `console.error`도 이슈로 올린다.
- 빌드할 때 소스맵을 올려 두어서, 압축된 코드가 아니라 원본 파일·줄 번호로 보인다.
- 읽는 곳: Sentry 대시보드 또는 `/admin/errors`.

### uptime — 살아 있나 확인 (앱 밖에서 · 5분마다)

- GitHub Actions가 5분마다 밖에서 `/api/health`를 두드린다.
- 응답이 없으면 워크플로가 빨간불이 되고 GitHub이 메일을 보낸다.
- 단, Actions의 cron은 정확하지 않아 10~20분 늦을 수 있다.

### 품질 측정 — 느려졌나 확인 (주 1회 · 월 09시)

- Lighthouse(모바일·데스크탑)·번들 크기·코드 건강을 자동 측정한다.
- 결과를 Supabase의 `quality_records`에 쌓아 품질 대시보드에서 추이로 본다.
- 무거운 작업(Chrome + 빌드)이라 CI에서만 돈다.

### 체감 속도 — 실제 사용자 수치 (사용자 브라우저에서)

- `web-vitals`가 실제 방문자의 로딩 체감치를 재서 `/api/rum`으로 보낸다.
- Vercel Analytics·Speed Insights, GA4도 함께 붙어 있다.
- 실험실 점수(Lighthouse)와 실사용 수치는 다를 수 있어 둘 다 본다.

## ⑨ 저절로 도는 것들 (Cron)

아무도 안 눌러도 정해진 시각에 저절로 도는 작업들. 시각은 모두 UTC로 적히므로 한국 시간과 9시간 차이가
난다.

| 하는 일                                              | 주기        | 한국 시간 | 설정된 곳                        |
| ---------------------------------------------------- | ----------- | --------- | -------------------------------- |
| 랭킹 스냅샷 저장 (`/api/cron/snapshot-rankings`)     | 매일        | 00:10     | `vercel.json`                    |
| 오래된 알림 정리 (`/api/notifications/cleanup`)      | 매일        | 11:00     | `vercel.json`                    |
| 요청 제한 기록 정리 (`/api/cron/cleanup-rate-limits`) | 매일       | 12:05     | `vercel.json`                    |
| 운영 사이트 헬스체크 (`/api/health`)                 | 5분마다     | 상시      | `.github/workflows/uptime.yml`   |
| 품질 측정 (Lighthouse·번들·코드건강)                 | 주 1회 (월) | 09:00     | `.github/workflows/quality.yml`  |

> Vercel Cron은 정해진 시각에 그냥 URL을 호출하는 것뿐이다. 아무나 그 주소를 두드릴 수 있으므로, 라우트가
> `CRON_SECRET`을 검사해서 Vercel이 보낸 요청인지 확인한다.

## ⑩ 헷갈리기 쉬운 말 정리

| 용어                       | 한 줄 설명                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| **Preview 배포**           | PR을 열 때마다 Vercel이 만들어 주는 임시 사이트. 코드는 운영과 같지만 붙는 DB가 다르다.      |
| **RLS (Row Level Security)** | "누가 어떤 행을 볼 수 있나"를 앱이 아니라 DB가 행 단위로 판정하는 규칙. 권한 없는 행은 에러 없이 그냥 빠진다. |
| **마이그레이션**           | DB 구조를 바꾼 내역을 SQL 파일로 시간순으로 쌓아 둔 것. 새 환경에서도 같은 순서로 재생하면 같은 DB가 된다. |
| **소스맵 (source map)**    | 배포용으로 압축·난독화된 코드를 원본 파일·줄 번호로 되돌려 주는 지도. Sentry가 이걸로 에러 위치를 알려 준다. |
| **모노레포 / Turborepo**   | 앱(`apps/page0127`)과 공용 패키지(`design-tokens`·`icons`·`quality`)를 한 저장소에서 함께 관리하는 방식. |
| **FSD (폴더 구조)**        | `src`를 `entities`·`features`·`widgets`·`shared`로 나눈 규칙. 아래 계층이 위 계층을 모르게 해서 의존 방향을 한쪽으로 고정한다. |
| **Server Component**       | 서버에서 렌더돼 HTML만 내려가는 컴포넌트. 이 프로젝트의 기본값이고, 상태·이벤트가 필요할 때만 `'use client'`를 붙인다. |
| **CI (Continuous Integration)** | PR을 올릴 때 자동으로 도는 검사. lint · 타입 · 단위 테스트 · 빌드 · 브라우저 스모크(E2E)까지 본다. |
| **Storybook**              | 컴포넌트를 앱에서 떼어내 하나씩 띄워 보는 작업대. 로그인·데이터 없이 버튼 하나만 확인할 수 있어, 상태별 모양을 빠짐없이 보기 좋다. |
| **RUM (Real User Monitoring)** | 실제 방문자의 브라우저에서 잰 로딩 체감 속도. Lighthouse가 실험실 점수라면 이쪽은 현장 기록이다. |

## ⑪ 아직 이 지도에 없는 것들 — 다음에 파고들 순서

순서는 "재미있어 보이는 것"이 아니라 **"이미 한 번 물린 것"**부터다. 아래 1~3은 전부 이 프로젝트에서 실제로
사고가 났던 자리다.

### 🩹 이미 물렸다

**1. DB 타입을 코드로 끌어오기**

- 지금: Supabase 클라이언트에 `Database` 제네릭이 없어서, 존재하지 않는 컬럼을 써도 타입 검사가 통과한다.
- 겪은 일: 집계 쿼리가 없는 컬럼을 참조했는데 빌드가 멀쩡히 성공했다.
- 시작점: `supabase gen types typescript`로 타입을 뽑아 `createClient<Database>()`에 물린다.
- 남는 것: 타입은 내가 손으로 쓰는 게 아니라 **스키마에서 생성되는 것**이다.

**2. 캐시가 몇 겹인지 알기**

- 지금: Next.js 캐시 네 겹(요청 메모이제이션 · Data · Full Route · Router)에 React Query `staleTime`이 또 얹혀 있다.
- 겪은 일: 로그아웃했는데 5분 동안 로그인 상태로 보였다. `router.refresh()`로는 안 지워지고 `queryClient.clear()`가 필요했다.
- 시작점: 로그아웃 흐름을 따라가며 "이 데이터는 지금 어느 층에 있나"를 한 겹씩 그려 본다.
- 남는 것: 화면이 안 바뀌면 코드보다 먼저 **"어느 캐시가 붙잡고 있나"**를 묻는다.

**3. 세션과 토큰의 수명**

- 지금: Supabase의 계정 정지는 refresh token 단계에서 막는 것이라, 이미 발급된 access token은 만료될 때까지(약 1시간) 살아 있다.
- 겪은 일: 정지시킨 계정이 곧바로 차단되지 않았다.
- 시작점: 브라우저 쿠키에 실제로 뭐가 들어 있는지 열어 보고, 미들웨어가 무엇을 검사하는지 따라간다.
- 남는 것: **"로그아웃시켰다"와 "토큰이 죽었다"는 서로 다른 말**이다.

### ⏳ 곧 아플 것

**4. 로그인이 필요한 흐름의 자동 테스트**

- 지금: vitest는 순수 함수만 보고, E2E에는 로그인 하네스가 없어 인증이 필요한 화면은 전부 손으로 확인하고 있다.
- 시작점: magiclink로 세션 쿠키를 만들어 Playwright `storageState`에 저장한다(로컬 검증용으로 이미 해 본 방식).
- 남는 것: 수동 검증은 바빠지는 순간 **"안 한 검증"**이 된다.

**5. 인덱스와 쿼리 실행 계획**

- 지금: 테이블이 27장인데 인덱스를 의식하고 만든 적은 거의 없다. 지금 빠른 건 데이터가 적어서다.
- 시작점: 피드·랭킹처럼 자주 도는 쿼리에 `explain analyze`를 걸어 어디서 시간을 쓰는지 본다.
- 남는 것: 느려지는 건 대개 컴포넌트가 아니라 **쿼리**다.

**6. 백업에서 되살려 보기**

- 지금: 백업은 Supabase가 자동으로 뜨고 있지만, 그걸로 **복원해 본 적이 한 번도 없다.**
- 시작점: 개발 프로젝트에 운영 백업을 부어 보고 걸리는 시간을 재 둔다.
- 남는 것: **해 보지 않은 복구 절차는 없는 것과 같다.**

> **이 지도가 이미 덮고 있는 범위** — 모노레포 · Server Component · 관리형 백엔드와 RLS · 마이그레이션 ·
> CI/CD · Preview 환경 분리 · 에러 추적 · 품질 자동 측정 · 실제 사용자 성능 수집 · 디자인 토큰과 Storybook ·
> 어드민 · AI 연동 · Cron. 위의 여섯은 이 위에 쌓는 **다음 층**이지, 처음부터 다시 배우는 목록이 아니다.
