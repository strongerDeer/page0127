>

## ① 전체 지도 — 코드가 사용자에게 닿기까지

왼쪽에서 오른쪽으로 흐른다. 내 노트북에서 시작한 코드가 GitHub을 거쳐 Vercel에서 빌드되고, 그 결과물이
사용자 브라우저에 뜬다.

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ STEP 1       │    │ STEP 2       │    │ STEP 3       │    │ STEP 4       │
│ 내 노트북    │ →  │ GitHub       │ →  │ Vercel       │ →  │ 사용자       │
│ (로컬)       │    │ (보관+검사)  │    │ (빌드+서버)  │    │ 브라우저     │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
```

| 단계                | 무슨 일이 일어나나                                                                  |
| ------------------- | ----------------------------------------------------------------------------------- |
| **1. 내 노트북**    | `npm run dev` + Docker로 띄운 Supabase. 여기서 짠 코드는 아직 세상 누구도 못 본다.   |
| **2. GitHub**       | 브랜치 → PR → main 순서로 올린다. PR마다 CI가 lint·타입·테스트·빌드·E2E를 자동 검사. |
| **3. Vercel**       | GitHub을 지켜보다가 코드가 올라오면 자동 빌드. PR이면 Preview 주소, main이면 운영 주소. |
| **4. 브라우저**     | `page0127.vercel.app`. 실제 사람이 보는 화면. 여기서 난 에러가 진짜 사고다.          |

### Vercel 서버가 바깥으로 말을 거는 곳

앱 혼자서는 아무것도 저장하거나 판단하지 못한다.

| 서비스            | 역할                                                                        |
| ----------------- | --------------------------------------------------------------------------- |
| **Supabase**      | Postgres DB + 로그인(Google OAuth) + 파일 저장 + 실시간 알림. 이 프로젝트의 심장. 환경마다 다른 프로젝트를 쓴다. |
| **OpenAI**        | 취향 분석 기능이 호출한다. 키는 서버에만 있고 브라우저로 절대 안 나간다.    |
| **알라딘 도서 API** | 책 검색과 표지 이미지를 받아온다. 역시 서버에서만 호출.                    |
| **Sentry**        | 에러가 터지면 여기로 보고가 간다. `/admin` 에러 탭에서 바로 읽을 수 있다.   |

## ② 환경 3개 — 로컬 · Preview · 운영

같은 코드가 세 곳에서 돈다. **코드는 같아도 붙는 데이터베이스가 다르다.** 이걸 헷갈리면 로컬에서 지운 게
운영에서 사라진다.

### 로컬 (내 컴퓨터)

| 항목             | 내용                                                            |
| ---------------- | --------------------------------------------------------------- |
| 어떻게 뜨나      | `bash scripts/dev.sh` → Docker Supabase 기동 후 `next dev`      |
| 주소             | `http://localhost:3000`                                          |
| 데이터베이스     | 내 PC 안 Docker 컨테이너 (DB `54322` · Studio `54323`)          |
| 로그인           | Google OAuth는 `localhost:3000`에서만 동작한다                   |
| 데이터의 무게    | 전부 가짜. `supabase db reset`으로 언제든 날려도 됨              |
| 언제 쓰나        | 기능을 만들고 부수며 실험할 때                                   |

### Preview (PR 미리보기)

| 항목             | 내용                                                            |
| ---------------- | --------------------------------------------------------------- |
| 어떻게 뜨나      | PR을 열면 Vercel이 자동으로 배포한다                             |
| 주소             | PR마다 다른 임시 URL (PR 코멘트에 붙는다)                        |
| 데이터베이스     | **개발용 Supabase 프로젝트** — 운영과 완전히 별개               |
| 안전장치         | CI가 운영 DB URL이면 빌드를 중단한다 (`npm run check:non-production-db`) |
| 데이터의 무게    | 실사용자 없음. 깨져도 사고가 아니다                              |
| 언제 쓰나        | 머지 전에 "진짜 서버에서도 되나" 확인할 때                       |

### 운영 (Production)

| 항목             | 내용                                                            |
| ---------------- | --------------------------------------------------------------- |
| 어떻게 뜨나      | main에 머지되는 순간 Vercel이 자동 배포                          |
| 주소             | `page0127.vercel.app`                                            |
| 데이터베이스     | **운영 Supabase 프로젝트** — 진짜 사용자의 기록                 |
| 로그인           | 도메인을 바꾸면 Supabase Site URL·Google Secret도 같이 갱신해야 한다 |
| 데이터의 무게    | 지우면 끝. 마이그레이션은 되돌리기 어렵다                        |
| 언제 쓰나        | 사용자가 실제로 쓰고 있는 바로 그것                              |

### ⚠️ 환경변수는 세 곳에 따로 산다

| 어디서 도나 | 환경변수를 읽는 곳                     |
| ----------- | -------------------------------------- |
| 로컬        | `apps/page0127/.env.local` 파일        |
| Preview·운영 | Vercel 대시보드의 환경별 설정          |
| CI          | GitHub Secrets                          |

이름은 같은데(`NEXT_PUBLIC_SUPABASE_URL` 등) 값이 다르다. **"로컬에선 되는데 배포하면 안 돼요"의 절반은
여기서 나온다.**

## ③ 요청 하나가 흐르는 길 (그리고 두 개의 열쇠)

사용자가 버튼 하나를 누르면 아래 순서로 움직인다. 중요한 건 4번 — **권한 판정은 앱 코드가 아니라
데이터베이스가 한다.**

```
1. 브라우저
   사용자가 "책 담기"를 누른다
        ↓
2. Next.js 서버 (Vercel 위)
   Server Component가 직접 조회하거나, app/api/… 라우트 핸들러가 받는다
        ↓
3. Supabase 클라이언트
   쿠키에 든 로그인 토큰을 함께 실어 Supabase로 보낸다
        ↓
4. Postgres + RLS
   "이 사람이 이 행을 봐도 되나"를 DB가 행 단위로 판정한다
        ↓
5. 허용된 데이터만 돌아옴
   권한 없는 행은 에러가 아니라 그냥 "없는 것"처럼 빠진다
   → 그래서 조용히 0건이 되기도 한다
```

### 🔑 Supabase에 들어가는 열쇠는 두 개다

**anon key — 손님용 열쇠** (`NEXT_PUBLIC_SUPABASE_ANON_KEY`)

- 브라우저에 그대로 노출돼도 괜찮다. 이 열쇠로 뭘 하든 RLS 규칙이 항상 먼저 검사하기 때문이다.
- 남의 비공개 기록은 이 열쇠로 절대 못 본다.

**service_role key — 만능 열쇠** (`SUPABASE_SERVICE_ROLE_KEY`)

- RLS를 통째로 건너뛴다. 모든 사람의 모든 행을 읽고 지울 수 있다.
- 서버 코드(admin 기능·크론)에서만 쓰고, 브라우저로 새어 나가면 DB 전체가 열린 것과 같다.

> **기억할 규칙 하나** — `NEXT_PUBLIC_`이 붙는 순간, 그 값은 빌드 결과물에 문자 그대로 박혀 브라우저로
> 나간다. 비밀값에는 절대 붙이지 않는다.

> **⚠️ RLS를 믿으면 안 되는 구간** — 여러 사용자를 가로지르는 집계·랭킹 쿼리는 RLS가 알아서 걸러 준다고
> 가정하면 안 된다. `is_public` 같은 공개 조건을 쿼리에 직접 써야 한다.

## ④ DB 변경이 세 환경으로 퍼지는 길

DB의 구조는 손으로 고치지 않는다. `supabase/migrations/`에 SQL 파일을 시간순 번호로 쌓아 올리는 방식 —
**DB판 git**이라고 생각하면 된다. (2026-07-29 기준 47개)

```
1. SQL 파일을 쓴다
   supabase/migrations/20260729000001_life_book_per_book.sql
   앞 숫자는 만든 시각. 이 순서대로 실행된다.
        ↓
2. 로컬에서 검증
   supabase db reset
   빈 DB에서 47개를 처음부터 다시 실행한다. 중간에 깨지면 여기서 바로 드러난다.
        ↓
3. PR → CI
   GitHub Actions가 검사. 번호 중복 검사도 여기 들어 있다.
        ↓
4. 개발 Supabase
   main에 머지된 뒤 개발 프로젝트에 적용. Preview·CI가 이 DB를 본다.
        ↓
5. 운영 Supabase
   supabase db push — 수동으로 적용. 자동이 아니다. 사람이 판단해서 누른다.
```

### ⚠️ 함정 둘

**번호가 겹치면 조용히 무너진다**

- 같은 번호의 파일이 두 개면 `db reset`이 그 지점에서 멈추고, 그 뒤 파일은 전부 적용되지 않는다.
- 내 폴더만 보면 안 보인다. 새 파일을 만들기 전에 **`origin/main`의 마지막 번호**를 확인할 것.

**순서가 뒤집히면 화면이 깨진다**

- 코드가 먼저 배포되고 마이그레이션이 나중에 적용되면, 앱은 아직 없는 컬럼을 찾다가 실패한다.
- 원칙은 **DB 먼저, 코드 나중.**

## ⑤ 감시 — 문제를 알아채는 네 개의 눈

"안에서 보는 눈"과 "밖에서 보는 눈"을 따로 둔 이유가 있다. **앱이 완전히 죽으면 앱 안에 심어 둔 감시도
같이 죽어서** 아무도 알려 주지 못하기 때문이다.

### Sentry — 에러 보고 (앱 안에서 · 실시간)

- 서버와 브라우저에서 터진 예외를 자동으로 모은다. 서버의 `console.error`도 이슈로 올린다.
- 빌드할 때 소스맵을 올려 두어서, 압축된 코드가 아니라 원본 파일·줄 번호로 보인다.
- 읽는 곳: Sentry 대시보드 또는 `/admin` 에러 탭.

### uptime — 살아 있나 확인 (앱 밖에서 · 5분마다)

- GitHub Actions가 5분마다 밖에서 `/api/health`를 두드린다.
- 응답이 없으면 워크플로가 빨간불이 되고 GitHub이 메일을 보낸다.
- 단, Actions의 cron은 정확하지 않아 10~20분 늦을 수 있다.

### 품질 측정 — 느려졌나 확인 (주 1회 · 월 09시)

- Lighthouse(모바일·데스크탑)·번들 크기·코드 건강을 자동 측정한다.
- 결과를 Supabase의 `quality_records`에 쌓아 품질 대시보드에서 추이로 본다.
- 무거운 작업(Chrome + 빌드)이라 CI에서만 돈다.

### 체감 속도 — 실제 사용자 수치 (사용자 브라우저에서)

- `web-vitals`가 실제 방문자의 로딩 체감치를 재서 `/api/rum`으로 보낸다.
- Vercel Analytics·Speed Insights, GA4도 함께 붙어 있다.
- 실험실 점수(Lighthouse)와 실사용 수치는 다를 수 있어 둘 다 본다.

## ⑥ 저절로 도는 것들 (Cron)

아무도 안 눌러도 정해진 시각에 저절로 도는 작업들. 시각은 모두 UTC로 적히므로 한국 시간과 9시간 차이가
난다.

| 하는 일                                              | 주기        | 한국 시간 | 설정된 곳                        |
| ---------------------------------------------------- | ----------- | --------- | -------------------------------- |
| 랭킹 스냅샷 저장 (`/api/cron/snapshot-rankings`)     | 매일        | 00:10     | `vercel.json`                    |
| 오래된 알림 정리 (`/api/notifications/cleanup`)      | 매일        | 11:00     | `vercel.json`                    |
| 요청 제한 기록 정리 (`/api/cron/cleanup-rate-limits`) | 매일       | 12:05     | `vercel.json`                    |
| 운영 사이트 헬스체크 (`/api/health`)                 | 5분마다     | 상시      | `.github/workflows/uptime.yml`   |
| 품질 측정 (Lighthouse·번들·코드건강)                 | 주 1회 (월) | 09:00     | `.github/workflows/quality.yml`  |

> Vercel Cron은 정해진 시각에 그냥 URL을 호출하는 것뿐이다. 아무나 그 주소를 두드릴 수 있으므로, 라우트가
> `CRON_SECRET`을 검사해서 Vercel이 보낸 요청인지 확인한다.

## ⑦ 헷갈리기 쉬운 말 정리

| 용어                       | 한 줄 설명                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| **Preview 배포**           | PR을 열 때마다 Vercel이 만들어 주는 임시 사이트. 코드는 운영과 같지만 붙는 DB가 다르다.      |
| **RLS (Row Level Security)** | "누가 어떤 행을 볼 수 있나"를 앱이 아니라 DB가 행 단위로 판정하는 규칙. 권한 없는 행은 에러 없이 그냥 빠진다. |
| **마이그레이션**           | DB 구조를 바꾼 내역을 SQL 파일로 시간순으로 쌓아 둔 것. 새 환경에서도 같은 순서로 재생하면 같은 DB가 된다. |
| **소스맵 (source map)**    | 배포용으로 압축·난독화된 코드를 원본 파일·줄 번호로 되돌려 주는 지도. Sentry가 이걸로 에러 위치를 알려 준다. |
| **모노레포 / Turborepo**   | 앱(`apps/page0127`)과 공용 패키지(`design-tokens`·`icons`·`quality`)를 한 저장소에서 함께 관리하는 방식. |
| **FSD (폴더 구조)**        | `src`를 `entities`·`features`·`widgets`·`shared`로 나눈 규칙. 아래 계층이 위 계층을 모르게 해서 의존 방향을 한쪽으로 고정한다. |
| **Server Component**       | 서버에서 렌더돼 HTML만 내려가는 컴포넌트. 이 프로젝트의 기본값이고, 상태·이벤트가 필요할 때만 `'use client'`를 붙인다. |
| **CI (Continuous Integration)** | PR을 올릴 때 자동으로 도는 검사. lint · 타입 · 단위 테스트 · 빌드 · 브라우저 스모크(E2E)까지 본다. |
